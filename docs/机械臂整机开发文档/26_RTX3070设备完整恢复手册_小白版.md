
## 8. 第 8 步：打关节阻尼补丁（**必做**）

**为什么**：厂家 URDF 的关节没有阻尼，仿真里会缓慢错位/抖动。这个坑排查了 10 小时。

**命令 22**（进目录）：

```bash

```

**命令 22-b**（⚠️ **先看补丁有没有打过 —— 千万别省这一步**）：

```bash
grep -c 'damping="5.0"' rm_eco65_gazebo.urdf
```

> ⚠️ **关键**：仓库里的源码**已经预置（bake 进）了阻尼补丁**，所以很可能根本不用再打。  
> 按显示的数字决定：
>
> | 显示     | 含义                 | 下一步                            |
> | ------ | ------------------ | ------------------------------ |
> | **6**  | 补丁已正确存在            | ✅ **跳过命令 23、23-b**，直接做命令 24 确认 |
> | **0**  | 还没打                | 继续命令 23 → 23-b                 |
> | **12** | **打重复了**（每个关节 2 条） | 立刻执行下面的「补救」                    |

**补救（显示 12 时）** —— 用备份恢复：

```bash
cp rm_eco65_gazebo.urdf.bak rm_eco65_gazebo.urdf
```

```bash
grep -c 'damping="5.0"' rm_eco65_gazebo.urdf
```

> 期望变回 **6**。  
> 说明：命令 22 做的备份 `.bak` 就是打补丁前的状态，也就是正确状态。


**命令 23**（备份，**只在命令 22-b 显示 0 时才需要**）：

```bash
cp rm_eco65_gazebo.urdf rm_eco65_gazebo.urdf.bak
```

**命令 23-b**（打补丁，**同样只在显示 0 时才需要**）：

```bash
sed -i 's|</joint>|  <dynamics damping="5.0" friction="0.1"/>\n</joint>|g' rm_eco65_gazebo.urdf
```

**命令 24**（确认生效）：

```bash
grep -c '<dynamics damping="5.0"' rm_eco65_gazebo.urdf
```

> 期望：数字 **正好 6**（6 个关节各一条）。
>
> ❌ **12** → 重复了，回去做「补救」。  
> ❌ **0** → 文件选错了，**必须是纯 `.urdf`，不是 `.urdf.xacro` 变体**。
>
> 💡 为什么要"正好 6"而不是"≥6"：URDF 里每个关节只能有一条 `<dynamics>`。  
> 有 2 条时多数解析器不报错（后一条覆盖前一条，效果碰巧一样），  
> 但状态不干净，转 SDF 时可能出警告。保持 6 最稳妥。

> ### 「清场」到底是什么意思？
>
> 🟢 **一句话：杀掉上一轮遗留的进程，一个文件都不会删。**  
> 你的代码、配置、文档全都安全。
>
> 打个比方：就像**打完一局游戏回主菜单再开新局**。  
> 不清的话，上一局残留的东西会在新一局里捣乱。
>
> 它会杀掉这些进程：
>
> | 进程                                          | 是什么           |
> | ------------------------------------------- | ------------- |
> | `gzserver` / `gzclient`                     | 仿真后台 + 仿真画面窗口 |
> | `robot_state_publisher`                     | 发布机器人模型的节点    |
> | `spawner.py` / `ros2 launch` / `gazebo_ros` | 启动器相关辅助进程     |
>
> 跑完会打印"剩余 gzserver: 0 / 剩余 robot_state_publisher: 0"，**都是 0 才算清干净**。
>
> ### 为什么必须清？
>
> 1. **端口占用**：上一轮的 Gazebo 还占着通信端口，新一轮会报  
>    `Address already in use`。
> 2. **⚠️ 更隐蔽的：僵尸进程抢发旧数据** —— 如果上一轮的  
>    `robot_state_publisher` 没死透，它会用"粘滞"消息持续发布**旧版机器人模型**，  
>    导致你改了 URDF，新一轮仿真里看到的还是旧的。  
>    这个坑曾让我们误判"环境不支持力矩接口"，白卡很久。
>
> ### 为什么不能自己用 `pkill` 代替？
>
> 因为 **`pkill -x robot_state_publisher` 从来就没生效过**！  
> Linux 把进程名截断到 15 个字符：
>
> ```
> robot_state_publisher   →   实际叫 robot_state_pub
> ```
>
> 名字对不上，就永远杀不掉。脚本里用的是**按完整路径匹配**的写法才有效。  
> 所以：**清场就跑这条命令，别自己敲 pkill。**

### 8.5.4 为什么一次抓取要两分钟？（不是卡住）

> 你问过"sim time 都快 2 分钟了，为什么这么慢"。答案是：
> **这 2 分钟里绝大部分是机械臂真的在走完这些动作**，不是卡顿。

脚本里的时间大致这么分：

| 阶段 | 耗时 |
|---|---|
| 张开手指 | 4s |
| 回标准姿势 + 等待 | 4s + 3s |
| 到观测姿势 + 等待 | 5s + 5s |
| **相机感知采集**（等点云稳定） | 最多 20s |
| 移到高点 + 等待 | 6s + 2s |
| 笛卡尔下降 6 步 | 12s + 2s |
| 预夹 | 3s |
| 恒力矩夹持 | 4s |
| 抬升 5 步 | 20s |
| 抬升后观察 40 次 | 20s |
| **合计** | **≈110 秒** |

**其中"感知 20s"和"抬升后观察 20s"占了近 40 秒**，是为了等数据稳定刻意留的。

#### 怎么判断是不是"真的慢"

看 Gazebo 的实时因子（RTF）：

```bash
timeout 5 gz stats
```

> 关注 `real time factor`：
> - **接近 1.0** → 仿真跟得上真实时间，上面的 110 秒就是正常耗时
> - **明显小于 1**（比如 0.3）→ 仿真跑不动，会额外拖慢，而且**控制会失真**
>   （实测表现：手指超调、预夹不到位）

#### 如果想更快（都有代价）

| 办法 | 效果 | 代价 |
|---|---|---|
| 关画面：`GZ_GUI=false` | 明显加快 | 看不到画面 |
| 真机用硬件渲染（已默认） | 加快 | 无（真机有 3070） |
| 减少感知/观察的等待 | 省约 40s | 数据可能不稳定，可靠性下降 |
| 增大 `max_step_size` | 物理步数减少 | **可能重现方块被压穿**，不推荐轻易改 |

> 💡 **建议**：先用默认（开画面）跑，确认没问题就行。两分钟是"机械臂认真干活"的时间，
> 真机上会更好看——你能同时看到画面。

```
------+---------+---------+---------+---------+---------+---------+----------
0000  |  0.0000 | ...
0060  |  0.0000 | ...   (Δj2=+0.0000)
...
```

| 现象                          | 判断                                      |
| --------------------------- | --------------------------------------- |
| **Δj2 全程 ±0.0000**，v_j2 ≈ 0 | ✅ 阻尼补丁生效，机械臂纹丝不动                        |
| Δj2 随时间**持续增大**             | ❌ **还在漂移**，说明阻尼补丁没生效（回到第 8 步，确认是"正好 6"） |

**关节顺序是 j2, j3, j1, j4, j5, j6，不是 j1~j6！** 这是睿尔曼硬件的注册顺序，

## 14. 第 14 步：手眼标定（**真机特有，必须做**）

> 仿真里相机外参是写死的精确值，真机没人告诉你相机装歪了多少。  
> **详细步骤见 `docs/机械臂整机开发文档/25_手眼标定操作清单.md`。**

**命令 43**（装依赖）：

```bash

```

**命令 44**（采集数据，半自动 —— 移好位姿按回车采一组）：


> ⚠️ 三个最容易翻车的点：
>
> 1. **`--square` 要填打印后实量的方格边长**（打印机常有几毫米误差）
> 2. **位姿之间必须有明显旋转**（>15°），只平移不旋转 → 标定方程退化，旋转解不出来
> 3. **标定板必须固定死**，中途动一下全废

> 旋转 < 0.1° 且平移 < 1mm = 优秀；< 0.5° 且 < 3mm = 可用；超标就重采。

> 💡 想看输入格式长什么样，可以打开 `recovery/samples_example.json` 参考。

**命令 46**（先验证求解器本身没问题，纯数学，不用真机）：

## 15. 第 15 步：夹爪堵转电流实测（真机特有）

仿真里我们用的是"恒定力矩 0.030 N·m"（指尖约 0.6 N/侧）。  
真机 MS42DC **只有位置模式**，要靠"过冲 + 堵转电流"等效。

**做法**：目标位置设得比物体表面再深 1~2mm → 电机转不动 → 堵转 → 由电流上限维持夹持力。

**命令 47**（先看夹爪能不能动 —— 通过 ROS 发指令）：

```bash
source /opt/ros/foxy/setup.bash && source ~/robot_vla_ws/install/setup.bash
```

```bash
ros2 topic pub /motor_control step_motor/msg/Motor "{id: 1, mode: 0, dir: 0, sub_divide: 0, angle: 100, speed: 50, state: 1}" --once
```

> ⚠️ **待真机验证**：参数含义来自 2026-10-25 读源码的结论（`step_motor` 包），  
> 但没在这台机器上跑过。先把输出贴给我。

**需要你实测并记录的 3 个数**：

| 要测的量                 | 怎么测        | 为什么              |
| -------------------- | ---------- | ---------------- |
| 夹爪闭合到不同开度时的**堵转电流**  | 堵住夹爪，读电流   | 建立"电流 ↔ 夹持力"对应关系 |
| 夹住 4cm 方块**不掉**的最小电流 | 逐步减小电流直到滑落 | 得到安全下限           |
| 与仿真 0.6 N/侧的换算       | 对比上面两个数    | 把仿真经验迁移到真机       |

> 理论值：方块重力 0.59 N，μ≈1.5 → 需要 **0.20 N/侧**。仿真给了 0.6 N/侧（3 倍余量）。

| 日志里世界名叫 `world[default]`（不是 `grasp_world`）        | `GZ_WORLD` 没传进 gzserver                                           | 跑 `grep GZ_WORLD ~/robot_vla_ws/install/rm_gazebo/share/rm_gazebo/launch/gz_demo_common.py`，没输出说明这份文件不支持该参数（需换成仓库里的新版本） |
