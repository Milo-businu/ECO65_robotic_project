## 二、头号坑：僵尸 robot_state_publisher（最值得讲）

### 现象

改 URDF 里的任何东西——接口类型、几何、惯量、插件——Gazebo 里**一律不生效**。
更糟的是，由此得出了一个**完全错误的结论**："本环境 ros2_control 只支持 position 接口"。

### 根因

Linux 内核里进程名 `comm` 被**截断到 15 个字符**：

```
robot_state_publisher   →   robot_state_pub
```

所以 `pkill -9 -x robot_state_publisher` **从来没有匹配到过任何进程**。
一个活了 6 天的旧实例就一直活着，用 ROS2 的 **latched（粘滞）QoS** 持续发布**旧版 robot_description**。
`spawn_entity` 拿到的是先到的那条旧消息，于是 Gazebo 里跑的永远是老模型。

### 修法

按**完整可执行路径**匹配，别用 `-x`：

```bash
pkill -9 -f "[/]robot_state_publisher/robot_state_publisher"
ps -eo args= | grep -c '[/]robot_state_publisher/robot_state_publisher'   # 计数
```

> `[/]` 是正则技巧：让模式字符串本身不匹配自己，避免把自己的 grep 进程算进去。

### 为什么值得讲

这不是"调参调对了"，而是**对工具链行为本身的质疑**。
大部分人遇到"改了不生效"会一直改配置；正确的反应是先问：**我改的东西到底有没有被读到？**
修完之后立刻推翻了一个已经写进记忆的"结论"——敢推翻自己的结论，这是很硬的工程素养。

## 三、核心物理问题：position 接口不是"控制"，是"瞬移"

### 现象

手指一路顶穿 4cm 方块；把关节 `<limit effort>` 改成 0.0001 N·m（几乎为零），
手指照样一瞬间从 0 跳到 0.2 rad。

### 根因（大白话）

Gazebo 的 `position` 命令接口不是"用力气把手掰到那个角度"，
而是**直接把关节的坐标改写成目标值**——相当于每帧瞬移。
既然是瞬移，那 `<limit effort>` 力矩上限当然管不着它，方块也挡不住它。

后果有两个，都是致命的：

1. **没有接触力**：动力学上这个关节"不存在受力"，ODE 算不出手指对方块施加了多大的力。
2. **过约束**：位置约束和"不可穿透"约束互相打架 → LCP 无解 → 数值发散（方块飞出几十米）。

### 修法

改成 **effort（力矩）接口**，手指变成真正受动力学驱动的物体：

| 参数 | 值 | 含义 |
|---|---|---|
| `TAU_GRIP` | 0.030 N·m | 恒定夹持力矩，指尖约 0.6 N/侧 |
| 方块重力 | 0.59 N | 0.06 kg × 9.8 |
| 需要的最小正压力 | ≈0.20 N/侧 | `0.59 / (2 × 1.5)`，μ≈1.5 |
| 实际余量 | **约 3 倍** | 既夹得住，又不会压爆接触 |

改完之后手指表现出了**真实的物理行为**：

```
力矩 +0.010 N·m → 手指不动（有静摩擦，推不动）   ← 真机也这样
力矩 +0.020 N·m → 手指平滑移动
力矩  0.000 N·m → 靠惯性继续滑一点再停
```

这段曲线本身就是"现在手指是柔顺的"的证据。

### 和真机的关系（面试加分点）

真机 MS42DC **只有位置模式**，没有力矩模式。
要在真机上复现"恒力矩"，做法是：**目标位置设得比物体表面再深 1~2mm**，
让电机堵转，由**电流上限**维持夹持力——物理上和仿真里"恒定力矩顶住"是同一件事。

> 能说出"仿真用扭矩、真机用堵转电流，二者物理等价"，说明你理解了**控制的本质是能量的受限传递**，
> 而不是记住了某个 API。

## 四、等效惯量：为什么手指会"抽风"

### 现象

改成力矩驱动后，手指角度在 0.02~0.07 之间乱跳，指令力矩在 ±0.09 之间振荡，根本到不了目标角。

### 根因（量化推导，这段面试很能讲）

原来手指惯量只算了裸连杆：`izz = 4.27e-6 kg·m²`。

```
角加速度 α = τ / I = 0.03 / 4.27e-6 ≈ 7000 rad/s²
```

而控制器只有 **100 Hz（周期 10ms）**。用阻尼项 KD=0.03 构成的一阶系统时间常数：

```
τ_sys = I / KD = 4.27e-6 / 0.03 ≈ 0.14 ms   ≪   控制周期 10 ms
```

**时间常数比控制周期小两个数量级 → 离散采样根本跟不上 → 数值振荡。**

### 修法（物理正确，不是凑数）

关节的等效惯量必须包含**电机经减速器的折算惯量**（Siciliano 教材动力学部分）：

```
J_eq = J_link + N² · J_rotor
```

取减速比 N=50、转子惯量 J_rotor=4e-7：

```
J_eq ≈ 50² × 4e-7 = 1.0e-3 kg·m²
```

改后时间常数 `1.0e-3 / 0.03 ≈ 33 ms`，是控制周期的 3 倍多 → **稳定**。

| 项 | 改前 | 改后 |
|---|---|---|
| `izz` | 4.27e-6 | **1.0e-3** |
| `ixx` / `iyy` | 1.607e-6 / 5.667e-6 | 6.0e-4 / 6.0e-4 |
| 关节阻尼 | 0.002 | 0.01 |
| 表现 | 剧烈振荡 | 力矩恒定 +0.0125，角度平滑爬升 |

> 临界判据（可以直接背）：**I > KD × 控制周期**。
> 这里 `0.03 × 0.01 = 3e-4`，取 1.0e-3 留了 3 倍余量。

## 五、URDF → SDF 会合并固定关节

### 现象

`gazebo_grasp_fix` 报：`Palm link gripper_base not found`。

### 根因

ROS 的 URDF 里 `gripper_base` 存在（`robot_state_publisher` 还照样打印它），
但 **Gazebo 加载时 URDF 会被转成 SDF，转换过程中固定关节（fixed joint）被合并**，
子 link 被并进父 link 然后消失。转换后的 SDF 里手指的父 link 是 **`Link6`**。

**通用规律**：凡是挂在 fixed 关节下的子 link，在 Gazebo 里都不存在。
（这也是为什么 `camera_link` 也消失、但相机插件还能用——传感器被并进了 Link6。）

### 修法

```xml
<palm_link>Link6</palm_link>   <!-- 不是 gripper_base -->
```

## 六、仿真器的两个"不靠谱"（gazebo_grasp_fix 适配）

插件是 JenniferBuehler 的 `gazebo-pkgs`，原版在本环境跑不通，改了 4 处：

| # | 问题 | 处理 |
|---|---|---|
| 1 | `palm_link` 写 `gripper_base` 找不到 | 改 `Link6`（见第五节） |
| 2 | `link->GetChildCount()` 取到的是子 link 数（常为 0），收集不到碰撞体 | 改 `link->GetCollisions().size()` |
| 3 | `ContactManager::CreateFilter` **永远收不到接触**（实测 hits=0，而默认话题明明有接触） | 直接订阅 `/gazebo/<world>/physics/contacts`，由插件自己按碰撞名筛选 |
| 4 | 两指接触力**总有一个恒为 0**，力判据 `CheckGrip` 永远不成立 | 增加**几何判据** |

### 第 4 点值得展开：为什么补几何判据是"对"的，不是"糊弄"

抓取理论里，判断能不能夹住（**力封闭 force closure**）本质上取决于
**接触法线方向和摩擦锥**，而不是某一瞬间力的大小。

原插件用力来判断，是因为正常情况下两指的力应该大小相当、方向相反。
但本环境 ODE 的接触力反馈不可靠（实测 `f1=(0,0,0) f2=(0,0,0)` 和
`(-4.15, 5.85, -6.95)` 同时出现），力判据就成了摆设。

补的判据是：**两个不同的夹爪 link 同时、持续地接触同一个物体 = 对捏成立**。
这正是力封闭的**几何前提**，比看瞬时力大小更符合理论。

> 面试话术：真机有真实的电流/力矩反馈，用不到这条；
> 这是**针对仿真器缺陷的等价替换**，不是放宽验收标准。

### 附带的一个坑

改订阅"全量接触话题"后，必须补 `else continue;`。
原代码在"两侧都不是夹爪碰撞体"时没有跳过，会拿空指针去 `->GetLink()` → 崩溃 / 除零。

## 七、「夹住又松开」—— 从怀疑 → 取证 → 定位 → 修复（✅ 已解决）

> 这一节是**整个项目最值钱的面试素材**：完整展示了"如何把一个偶发故障查成必然结论"。

### 现象

成功一次（`dz = +0.0978 m`），同样代码再跑又失败（`dz = 0`），**成功率约 50%**。
标记文件显示：成功时 `links=2`（两指同时接触）持续出现；
失败时 `links=2` 只闪了 6 下，多数时刻 `links=1` → 吸附后计数掉下去 → 被松开。

### 取证：拿到确凿证据（这一步是关键）

之前只是"怀疑"参数有问题。真机实跑时在 Gazebo 控制台日志里抓到了决定性证据：

```
GazeboGraspFix: Attaching  target_box::link::collision to gripper   ← 夹住了
GazeboGraspFix: Detaching  target_box::link::collision from gripper ← 立刻松开
```

**`Attaching` 紧跟 `Detaching`** —— 这证明不是"没夹住"，而是**夹住之后又被判定为松开**。
把故障范围从"夹持力不够/几何不对"一下子缩小到"吸附后的判定逻辑"。

### 根因（证实）

`disable_collisions_on_attach=true` 自相矛盾：

```
吸附成功 → 插件【禁用方块与手臂的碰撞】→ 接触消失
        → 插件判定"不再夹持" → grip count 递减 → detach → 松开
```

**参数本意是好的**（吸附成功后禁用碰撞，避免手指穿过物体这种伪影），
但它**破坏了自己判定"是否还夹着"的依据**——判据就是接触。

### 修复

改成 `false`：

```xml
<disable_collisions_on_attach>false</disable_collisions_on_attach>
```

> 💡 为什么敢改：手指此时已经是**力矩驱动（柔顺）**，
> 保留碰撞也不会把方块挤压引爆。**这正是"先改驱动方式，再改插件参数"的好处**——
> 顺序对了，后面的参数才有调整空间。

### 验证

| 检查 | 结果 |
|---|---|
| 控制台日志 | **只有 `Attaching`，无 `Detaching`** ✅ |
| `MARKER ATTACH` | 触发 1 次 ✅ |
| 闭环 | **`dz = +0.0991 m` → 夹起来了**，且**一次成功** ✅ |

**成功率从约 50% 变成稳定成功。**

### 面试怎么讲（加分点）

不要讲成"我改了个参数就好了"，要讲成一条**证据链**：

1. 现象：50% 概率失败 → 说明**不是能力问题，是稳定性问题**
2. 取证：不满足于"怀疑"，去找**能证伪/证实的日志证据**（Attaching 紧跟 Detaching）
3. 定位：由证据排除"夹持力不够"，锁定"吸附后的判定逻辑"
4. 机理：说出**参数本意与判据的冲突**（禁用碰撞 ⟂ 靠接触判定）
5. 修复 + 验证：改完要拿**可量化的前后对比**（50% → 一次成功）

> 追问预案："你怎么确认改这个参数不会引入新问题？"
> → 因为手指已是力矩驱动（柔顺），保留碰撞不会挤压引爆；且实测 dz 正常、无 NaN。

## 八、夹爪同轴建模：一次几何修正牵动六处（2026-10-29）

### 现象

看仿真画面发现：**夹爪垂直于机械臂末端旋转轴**。真机应该是**同轴**的。

### 取证（不靠直觉，实测）

直觉会以为"末端旋转轴是竖直的"。实测零位 FK 后发现**完全相反**：

| 零位时 Link6 的轴 | 世界方向 |
|---|---|
| x 轴 | `[1, 0, 0]` 水平 |
| y 轴 | `[0, 0, -1]` 朝下 |
| **z 轴** | **`[0, 1, 0]` 水平** |

再查 URDF：`joint6` 的 `<axis xyz="0 0 1"/>` → **Link6 的 z 轴就是末端旋转轴**。
而原来夹爪沿 **x 轴**装 → 与末端轴垂直 → 确实是错的。

### 改动清单（牵一发动全身，共 6 处）

| # | 改动 |
|---|---|
| 1 | 夹爪挂载 joint 加 `rpy="0 -1.5708 0"`（局部 x → Link6 +z） |
| 2 | 本体 0.1655→**0.145**、手指铰链同步 → 指尖总长 **0.195**（法兰→指尖，含手指） |
| 3 | 相机移到夹爪侧面 `(0.05, 0, 0.13)`，光轴随夹爪 |
| 4 | `TCP_OFF=[0,0,0.195]`、`CAM_OFF=[0.05,0,0.13]`、新增 `CAM_ROT` |
| 5 | **姿态约定改为「工具 z 轴 = 夹爪纵轴」**：`orthonormal_basis` 以 z 为基准、滚转改 `rot_z`、IK 把 down 放第三列 |
| 6 | 高点 0.25→**0.16**：夹爪加长后 TCP 高于约 **0.22 就 IK 无解**（高度扫描确认） |

### 面试价值

这是一次**真实的机械建模 → 运动学联动**案例，能讲三层：

1. **几何对齐**：真机是 19.5cm 同轴长夹爪，仿真必须一致，否则后面所有标定/抓取都是假的
2. **运动学联动**：改一个安装方向，会连带改 TCP、姿态约束、相机偏移、可达空间——**不是改个数就完事**
3. **可达性验证**：加长夹爪后要**重新扫高度**，确认关键路径点仍有解（扫描出 0.22 是上限）

## 九、相机带转向后，坐标变换公式失效（隐式约定坑）

### 现象

给相机加 `-90°` 转向后，感知结果飘到 `[0.561, 0.409, 0.405]`
（方块实际在 `[0.40, 0, 0.02]`）。

### 根因

`localize` 里这行：

```python
ests.append(R6 @ (CAM_OFF + p_body) + t6)
```

它把 `CAM_OFF`（Link6 系）和 `p_body`（相机系）**直接相加**。
这只在**相机与 Link6 同姿态**时成立——原来 `rpy="0 0 0"` 确实同姿态；
加转向后**约定失效**，但代码不会报错，只会算出错误的数。

### 修复

```python
ests.append((R6 @ CAM_ROT) @ p_body + (t6 + R6 @ CAM_OFF))
```

离线验证：新公式 `[0.05, 0, 0.43]` ✅，旧公式错成 `[0.35, 0, 0.13]` ❌。

### 面试价值（这个项目最通用的教训）

> **给某个坐标系加旋转后，必须全局搜所有"假设两系同姿态"的代码**
> —— 向量直接相加、直接复用父系旋转矩阵，这类**隐式约定**最容易漏，
> 而且**不报错、只给错结果**，是最难查的一类 bug。

**追问预案**："这类问题怎么预防？"
→ ① 改动涉及坐标系时，先列出所有用到该系的地方；
② 对坐标变换写**离线数值验证**（构造已知点，检查算出来对不对），不要只在仿真里看。

## 十、面试：项目一句话介绍（三个版本）

### 30 秒版

> 我做的是一个**语言驱动的机械臂抓取系统**的仿真验证环节。
> 用腕部深度相机感知桌面上的方块，自己算逆运动学规划轨迹，
> 笛卡尔直线下降、力矩夹持、直线抬升。
> 目前能把 4cm 的方块稳定抬起约 10 厘米，水平误差不到 1 毫米。

### 2 分钟版（加技术深度）

> 系统分四层：感知用腕部相机点云拟合物体顶面；
> 规划用阻尼最小二乘逆运动学，配合滚转角搜索保证夹爪姿态和物体表面对齐；
> 执行层手臂走位置轨迹、夹爪走力矩控制；
> 底层是 Gazebo/ODE 物理仿真。
>
> **最有价值的一段是夹爪驱动方式的改造**。一开始用位置接口，发现方块要么被顶穿、
> 要么被弹飞几十米。查下来发现位置接口在 Gazebo 里是运动学置位——关节被直接改写坐标，
> 物理引擎根本不产生接触力。改成功矩控制之后，手指才有了柔顺性，
> 表现出了和真机一样的静摩擦、堵转行为。

### 5 分钟版（加工程素养）

> 这个项目里我最想讲的其实不是算法，是**一次误判的纠正**。
>
> 我们一度得出结论"这个仿真环境只支持位置接口"，还写进了项目记忆。
> 后来发现是 Linux 进程名被内核截断到 15 个字符，导致清理脚本里的
> `pkill -x robot_state_publisher` 从来没生效过。
> 一个活了六天的僵尸进程一直在用粘滞 QoS 发布旧版机器人描述，
> 所以我们改的所有 URDF 根本没进仿真器。
>
> 修掉之后重测，力矩接口其实是支持的——**之前那个结论是错的**。
> 这也直接解开了"方块夹不起来"这个卡了很久的死结。
>
> 我的体会是：当"改了没效果"的时候，第一反应不该是继续改配置，
> 而应该先验证**我改的东西到底有没有被读到**。

## 十一、高频追问预案

| 追问 | 回答要点 |
|---|---|
| **为什么不用现成的 MoveIt 抓取？** | 目标是把感知→规划→控制整条链吃透并可控；MoveIt 在这套 Foxy 环境里有 panda 依赖问题，且无法暴露接触动力学细节。 |
| **位置和力矩控制到底差在哪？** | 位置是"指定坐标"，力矩是"指定受力"。前者在仿真里等价于瞬移，绕过了动力学；后者让关节真正参与求解，才能产生接触力、才能被物体挡住。 |
| **为什么一定要笛卡尔直线？** | 关节空间插值会让 TCP 走弧线，刚性手指横向拖拽物体，接触力突增会弹飞（实测飞出 1 米多、甚至几十米）。直线下降保证只有法向接近、没有横向扫。 |
| **惯量那个 1.0e-3 是怎么来的？** | 不是凑的。`J_eq = J_link + N²·J_rotor`，减速比 50、转子惯量 4e-7 算出来就是这个量级。稳定性判据是 `I > KD × 控制周期`。 |
| **仿真过了真机就能过吗？** | 不能。仿真里的 `gazebo_grasp_fix` 吸附是补丁，真机不需要；真机夹爪只有位置模式，要用"过冲 + 堵转电流"等效恒力矩；还有手眼标定误差、相机盲区、线缆弯折这些仿真看不到的问题。 |
| **你怎么判断一个 bug 是不是真 bug？** | 看它会不会带到真机。惯量建模、夹爪几何、轨迹方式都会带过去，是真 bug；插件参数、接触判据只在仿真里存在，是仿真适配。 |
| **数值发散（NaN / 方块飞走）怎么排查？** | 先看是过约束还是刚度过高。位置约束 + 不可穿透 = 过约束，改力矩即可；接触刚度 kp 与电机能力势均力敌时会炸，拉开量级就好。 |
| **有没有改被测对象来让结果好看？** | 没有，这是红线。方块的真值只用来做诊断交叉校验，从不喂给程序（没有设 `<static>` 之类的）。 |

## 十二、这个项目能证明的能力（挑 4 条讲）

1. **能从现象反推到根因**——不是"调参调好了"，而是搞清楚"为什么位置接口不产生接触力"。
2. **敢推翻已有结论**——发现六天前的错误结论后立刻重测并纠正。
3. **物理直觉**——知道夹爪该用电流限制、知道惯量要含折算项、知道力封闭看的是法线不是力的大小。
4. **工程边界感**——分得清"会带到真机的真 bug"和"只在仿真里存在的适配"。

## 十四、从仿真到真机的迁移清单

| 项 | 仿真 | 真机 | 动作 |
|---|---|---|---|
| 相机驱动 | Gazebo 插件 | librealsense + realsense-ros | **型号未定 → 版本钉不死，首要阻塞** |
| 手眼标定 | 已知精确外参 | 需实标（眼在手） | 补标定流程 |

| 安全 | 无 | 力矩/碰撞保护 | 必须加 |
