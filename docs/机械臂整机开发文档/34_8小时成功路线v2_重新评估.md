## 0. 先说结论：一天能不能成

能。但**不是靠"每一步都做对"，而是靠三件事**：

1. **前 45 分钟只干一件事**：让 `/joint_states` 出数。它不出来，后面 7 小时全是空转。
2. **把"标定精度"换成"四个锚点"**：夹爪 `max_width`、`tcp_offset`、手眼 X 的平移、深度尺度。
   四个里已经有三个闭合【实测】，只剩 X。
3. **把"任务跑通"和"视觉闭环"解耦**：视觉不收敛也能用示教点跑完整任务。
   这样"一天内完成"不再取决于标定这一件不确定的事。

**成功率估计（我的判断，不是保证）**

| 级别 | 含义 | 估计 |
|---|---|---|
| **L1 任务跑通** | 抓起来 → 放到固定区，位置靠示教（`fixed_target_xyz`） | **≥95%** |

> 一天的时间盒按 **L2 为主线、L1 为兜底** 排。到 15:20（第 3:50 段）如果手眼还没过打点，
> **立刻切 L1**，先把任务做完；剩下的时间再回头修视觉。这样"必须成功"就有了下限。

## 2. 关键路径：钱花在哪

```
    链路(45min) ──► 夹爪锚点(25min) ──► 手眼(110min) ──► 抓取(60min) ──► 放置(40min)
        │                 │                  │                │
        │                 │                  └─ 止损1：打点 spread>5mm → 切 L1 兜底
        │                 └─ 止损0：空夹开口≠37±2 → 先修 max_width，别往下走
        └─ 止损－1：45min 还不见 /joint_states → 停手查网卡，别试代码
```

**为什么手眼给 110 分钟而不是 2 小时**：
采集 8~12 组，每组"摆臂 + 回车 + 看一行重投影"约 1.5~2 分钟【推导】= 20 分钟；
真正耗时间的是**第一次让 ArUco 被检测到**（纸翘、光照、字典、边长）和**填配置/验证**。
把 2 小时压到 110 分钟，省下的时间给第 5 段的 5 次重复——**重复次数比标定精度更影响最终成功率**。

## 3. 六道门（每道都有 GO 判据和失败动作）

### G1 链路门（0:00–0:25，硬止损 0:45）

```bash
cd ~/robot_vla_ws
source /opt/ros/foxy/setup.bash

# 一条命令配平 arm_ip / udp_ip（会 ping 机械臂、探 8080）
python3 robot_code/arm_grasp/scripts/net_autoconf.py

# 起链路（不自动抓）
ros2 launch arm_grasp real_grasp.launch.py start_task:=false

# 另一个终端：唯一判据
timeout 3 ros2 topic echo /joint_states
```

| GO | 失败动作 |
|---|---|
| `/joint_states` **有 6 个关节角在刷**（≥10Hz） | ① 看 `hostname -I` 有没有 `192.168.1.x`；② 没有就配静态 IP（脚本会打印 `nmcli` 命令）；③ 有 IP 但仍无数据 → 重启 rm_driver；④ 还不行 → 换网线/USB 网卡 |

> 【实测】这一步最大的坑是 `udp_ip` 填错，而它**不会**产生任何"IP 错误"提示，
> 只会让你在感知层看到"收不到关节角"。所以判据只认 `/joint_states`，不看日志措辞。

### G2 夹爪锚点门（0:25–0:50）

```bash
# 单独起夹爪节点（不要同时开着整机 launch，串口独占）
python3 robot_code/arm_grasp/scripts/gripper_node.py &
ros2 topic pub --once /gripper/cmd std_msgs/msg/String "data: 'home'"
# 等 7 秒，然后【拿卡尺量两指内侧距离】= 真值
ros2 topic pub --once /gripper/cmd std_msgs/msg/String "data: 'grip:40'"
# 等 7 秒，再量一次
```

| 测量 | 期望 | 不符合怎么办 |
|---|---|---|
| home 后开口 | **≈ `max_width_mm`**（配置里 120） | 量到多少就把 `max_width_mm` 改成多少【实测锚点】 |
| `grip:40` 空夹开口 | **37 ± 2mm** | 差值 = 锚点误差：`max_width_mm += (读数 − 37)` |
| 同时看 `/gripper/state` | 记下 `[开口, 角度, 到位, 堵转]` 四个数 | 这就是 G6 判"夹空"的基准 |

**为什么这条能毁一天**【推导】：
`gripper_node` 用 `(max_width_mm − 目标开口)` 算要发多少度。若 `max_width` 比真实值**大 10mm**，
第一次从 home 闭合就少关 10mm → 预夹 52mm 实际变 62mm、夹持 37mm 实际变 47mm → **两指碰不到 40mm 方块**，
现象是"下去了、夹了、抬起来什么都没有"，而你会以为是手眼偏了。

**顺手确认"夹空 vs 夹到"的语义**（30 秒）：

| 场景 | 期望 state |
|---|---|
| 空夹（指间无物） | 到位=1、堵转=0（电机走到了目标开口） |
| 夹 4cm 方块 | 到位=0、堵转=1（到不了目标开口，顶住了） |

把实际读数写在纸上。**这两个标志是后面所有"为什么没夹住"的判断依据**；
如果实测与上表相反，第 7 阶段那句提示就要反着读（代码只报警不中止，故意如此）。

### G4 光轴 / 观察位 / 颜色 / 放置点（1:10–1:30，四件小事）

**G4-a 光轴判定（3 分钟，决定后面所有事）**

### 3.5 作业区：别用 1m×1m，先量出来（1 分钟，不动机器人）

你说 1m×1m 只是预估——对，而且**差得很多**。ECO65 半径 0.627m【实测参数】，
以底座为原点的 1m×1m 方块不可能全可达。这个数直接决定：标定板摆哪、
方块摆哪、放置区在哪、观察位要不要那么大视场。

```bash
python3 robot_code/arm_grasp/scripts/workspace_map.py            # 约 1 分钟（纯 IK 扫格）
python3 robot_code/arm_grasp/scripts/workspace_map.py --surface-z 0.02
```

它在三个高度（抓取 / 抬升 / 转运）上逐格做 IK，判据是**工具 z 轴竖直向下**
（和抓取时完全一致），打出一张 ASCII 图。云机按 URDF 跑出来的结果【推导，可复算】：

| 区域 | x 范围 | y 范围 | 面积 |
|---|---|---|---|
| **三层都可达**（稳定作业区） | 0.12 ~ 0.40 m | ±0.34 m | **≈0.19 m²** |
| 仅抓取高度可达 | 0.12 ~ 0.48 m | ±0.34 m | — |

也就是说：**能稳定抓+抬+运的地方只有约 0.19 m²，是你预估的 1/5**，
而且 x 超过 0.40m 之后虽然够得到，但抬不高、运不了。

所以：
- 方块放在 **x 0.25~0.35、y ±0.15** 这一小片，别摊在 1m 的桌上
- 标定板放 **x 0.15~0.37、y ±0.30**（脚本会直接打印这个建议区）
- 放置区选一个跟抓取区有距离但不贴边的点（脚本给三个候选）
- `task.work_aim_m` 已按实测改成 `[0.30, 0.0, 0.02]`（原来写 0.40，正好在边界上）

> 这张图是**几何可达**，不含碰撞。真机第一次动之前，仍要用 `jog.py` 把指尖
> 挪到目标点上方确认没障碍。

### G5 手眼门（1:30–3:20，**硬止损 3:20**）

完整流程见第 4 节。判据：

| 层 | 判据 | 不过怎么办 |
|---|---|---|
| L1 数学 | 求解残差 **< 5mm**（本项目无外力，超过就是数据有问题） | 看 4.4 分层表 |
| L2 量级 | 自动检查：`|t|` 在 2~45cm、旋转正交 | 单位错 / 抄错 / A·B 定义反 |
| L3 物理 | **`verify_handeye.py` 4 点打点，去均值后残差 < 5mm** | spread 大 → 重标；spread 小 → 补偿 |

> **L3 是本项目唯一可信的验收**。残差小（L1）只说明数据自洽。
> 33 号里那串 `--probe 2.1 1.8 2.6 3.0 2.4` 是"人自己想办法量出 5 个数字"，
> 现场根本落不了地——这是原计划最大的可操作性缺口，现在换成了脚本。

## 4. 手眼专项 v2

### 4.1 采集：自动扫位（6 分钟，不需要示教器）

原来的做法是"人用示教器摆 12 个位姿"，但真机 Ubuntu 不适配示教器，这条路直接断了。
现在改成**机械臂自己走 15 个预设位姿**，人只负责把它领到起点：

```bash
cd ~/robot_vla_ws
# 终端 A：起链路（夹爪节点会占串口，但这里不用它，无妨）
ros2 launch arm_grasp real_grasp.launch.py start_task:=false

# 终端 B：先用键盘把臂挪到「相机明显对着 A4 板」的位姿（这一步代替示教器）
python3 robot_code/arm_grasp/scripts/jog.py --step 20
#   w/s/a/d 平移、r/f 升降、i/k/u/o/j/l 转、1~6 改步长、c 打印当前位姿、q 退出
#   退出前记一下位姿（按 c 会打印），扫位失败时好回到这里

# 终端 B：自动扫位采集（会自己动，约 1.5 分钟）
python3 recovery/collect_handeye.py --sweep --marker-size 0.0595 \
    --out ~/handeye_samples.json
```

扫位序列（脚本内置，共 15 个候选）：

### 4.5 物理打点 + 常数偏置（10 分钟，别跳）

```bash
python3 robot_code/arm_grasp/scripts/verify_handeye.py --points 5 --marker-size 0.0595
```

它做的是（每点一次）：

1. 相机看到 ArUco → 用 X 算出标记中心在基座系的位置 P
2. 把指尖开到 P 正上方 2cm（低速、先抬高再平移）
3. **你用键盘把指尖微调到正好压在标记中心上**（脚本自带微调模式；眼睛能判 ~1mm）
4. 回车 → 它读这一刻的关节角，用 **FK 算出指尖真实位置 P'**（完全不经过相机）
5. 误差 `c = P' − P`

> 为什么这不是循环论证：P' 来自编码器 + URDF + `tcp_offset`，与手眼矩阵无关。
> 为什么要 4 个点：**c 一致 = 常数偏置（能补）；c 乱 = 旋转/尺度错（补不了，只能重标）**。
> 为什么不拿方块当基准：方块是被测对象，拿它的真值去校程序就是作弊（工程伦理红线已定）。
> ArUco 是标定基准物，用它做参考是标定的正常做法。

输出两种结论：

```
✅ 去均值后残差 < 5mm → 直接给一行 perception.xy_bias_m，填进配置就能抓
❌ > 5mm            → 按提示查 marker 尺寸 / tcp_offset / 姿态激励
```

**偏置什么时候必须清零**：换标定、换相机安装、换 `tcp_offset` 之后。它补的是固定误差，不是万能胶。

## 附录 B：三个容差的推导（可复算，不是拍脑袋）

**① 横向误差容限**：预夹开口 `W = 40 + M`（M = `pregrip_margin_mm`）。
两指各在 ±W/2。要让 40mm 方块落在指间，需 `W/2 > 20 + δ`，即

```
δ < M/2
M=8  → δ < 4mm     M=12 → δ < 6mm
```

**② 方块摆歪容限**：方块投影宽度 = `40·(|cosθ|+|sinθ|) = 40√2·sin(θ+45°)`，要求 ≤ W：

```
M=8  → |cos|+|sin| ≤ 1.20 → θ ≤ 13.1°
M=12 → ≤ 1.30            → θ ≤ 25.0°
M=14 → ≤ 1.35            → θ ≤ 27.7°
```

这就是把 `pregrip_margin_mm` 从 8 改成 12 的理由：摆歪容差从 ±13° 变成 ±25°，
代价只是两指多张 4mm。

**③ 为什么"3mm 验收"是这套几何的产物**：
竖向下降时方块必须整体落在两指之间 → `δ < M/2`；M=8 时 4mm、M=12 时 6mm。
但还要留滑动/标定余量，所以**任务级可用阈值取 M/2 的 2/3**：M=8 → 2.7mm（≈3mm），M=12 → 4mm。
换句话说：33 号那个"3mm"在 M=8 下是对的，改到 M=12 后**可以放宽到 4mm**——
这能省下大量"为了 0.5mm 重标一次"的时间。

```
r / f   抬升 / 下降               1 ~ 6   步长 0.5 / 1 / 5 / 10 / 20 / 50 mm
i / k   绕工具 x 俯仰 ±           u / o   绕工具 y 滚转 ±
j / l   绕工具 z 偏航 ±           +       旋转步长 2° → 5° → 10°
g 打印位姿   c 打印配置片段   h 回 home（要确认）   x 急停   q 退出
--joint 模式：1~6 选关节，w/s 微调该关节
```

设计上的三条保险（因为看不见人、只能靠终端）：
1. 单步关节跳变 > 0.6 rad **直接拒绝**并提示减小步长（防突然翻腕）
2. 速度强制 ≤10（比抓取任务更慢）
3. 起手先打印当前位姿；每步之后都打印新位姿，便于发现"没动/动多了"

> 如果遥控终端（SSH）里按单键没反应：`jog.py` 用的是 termios 单键读取，
> 需要真终端。远程时请在本机开终端，或改用 `verify_handeye` 那种回车确认式交互。

## 附录 E：端到端识别「大脑」怎么选、怎么接（可选，默认关）

**定位先说清**：它不是替代 IK/夹爪的 VLA，只接管"目标在哪"这一步。
分工是 **大脑给 2D 框 + 名字 → 几何给 3D 点**。理由：让 VLM 直接吐 3D/动作，
精度远不如"框中心 + 对齐深度反投影"，而且错了没法归因。

### E.1 模型选择（RTX 3070 8GB）

| 模型 | 量化 | 显存 | 本机 8GB | 说明 |
|---|---|---|---|---|
| **Qwen2.5-VL-3B-Instruct** | Q4_K_M + mmproj | **≈5~6 GB** | ✅ 首选 | 能"认+说"，给 bbox 也稳；留得下相机 pipeline |
| Qwen2.5-VL-7B | Q4_K_M | ≈7.1 GB（90%） | ⚠️ 紧 | 抓取/标定同机跑不建议 |
| Florence-2-large 0.77B | FP16 | ≈1.5 GB | ✅ 很轻 | 只会给框不会"讲"；只要检测时更划算 |

【外验】以上为 2026-11 检索到的第三方测算（含 mmproj 与 KV cache），**本机未实测**。
装好后用 `brain.py --check` 看真实延迟，>1.5s 就换更小的或降分辨率。

### E.2 三种跑法（都不动 ROS 环境）

真机是 Ubuntu 20.04 + Foxy + **Python 3.8**，主流推理框架早不支持 3.8，
所以模型必须跑在独立环境里，机器人只发 HTTP：

```bash
# 方式 A：Ollama（最省事）
ollama pull qwen2.5vl:3b
#   url: http://127.0.0.1:11434/v1/chat/completions   model: qwen2.5vl:3b

# 方式 B：LM Studio（图形界面，能看显存占用）
#   起 Local Server → 端口 1234 → url: http://127.0.0.1:1234/v1/chat/completions

# 方式 C：vLLM（要 conda py3.10，吞吐最好）
conda create -n vl python=3.10 -y && conda activate vl
pip install vllm && vllm serve Qwen/Qwen2.5-VL-3B-Instruct --port 8000
#   url: http://127.0.0.1:8000/v1/chat/completions
```

### E.3 接进来（两步，随时可切回）

```yaml
perception:
  target_source: brain        # color（默认）| brain
  target_name: "green cube"   # 要认什么；英文通常更准，"apple" / "red block" 都行
brain:
  enabled: true
  url: "http://127.0.0.1:11434/v1/chat/completions"
  model: "qwen2.5vl:3b"
  fallback_to_color: true     # 大脑没给结果时本轮退回颜色阈值，不至于停摆
```

```bash
python3 robot_code/arm_grasp/scripts/brain.py --check     # 先自检：能否连通、延迟、框对不对
ros2 launch arm_grasp real_grasp.launch.py start_task:=false
timeout 5 ros2 topic echo /grasp/target_xyz
```

切回颜色阈值：一条命令 `python3 robot_code/arm_grasp/scripts/perception_mode.py color`
（它会把 `brain.enabled` 一起关掉、释放显存）。

> **逐步操作、逐条判据、三个"配了没生效"的坑，见 `35_感知两种模式操作手册_color与brain.md`。**

### E.4 什么时候值得开大脑

| 场景 | 用 color | 用 brain |
|---|---|---|
| 4cm 纯色方块、光照稳定 | ✅ 更快更稳 | 没必要 |
| 要认"苹果/杯子/红色积木"等开放词汇 | ❌ 不支持 | ✅ |
| 方块颜色和桌面接近 | ⚠️ 阈值难调 | ✅ 语义可分 |
| 追求最短链路、可解释 | ✅ | ❌ 有 0.5~2s 延迟与不确定性 |

> 建议：**明天主线仍用 color**（L1/L2 都靠它），brain 作为"进阶任务的入口"先接通自检，
> 等抓取闭环稳定后再切过去做泛化实验。VLA（`task.policy: vla`）保持现状不动。
