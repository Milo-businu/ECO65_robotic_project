## 4. 灭掉的三个真 bug（本阶段最大含金量）

| # | bug | 决定性证据 | 修复 |
|---|-----|-----------|------|
| 1 | **光学系约定**：点云是"z 前向"不是"x 前向" | 3D 点与光轴夹角 60°（对不上），与 z 轴夹角 **29.6° ≈ 像素偏角 30°** | `p_link = M @ p_opt`，M = [[0,0,1],[−1,0,0],[0,−1,0]] |
| 2 | **非结构化点云**：Foxy 深度相机点云是 height=1 的一维长条 | 报"无法按像素索引" | 行优先展开 `idx = v*width + u`（校验点数 == w×h） |
| 3 | **时钟源不一致**：点云戳=仿真时钟(610s)，TF=墙钟(1792481788) | `Lookup would require extrapolation into the past` | 取最新 TF（`Time()`）；长期正解统一 `use_sim_time` |

> 这三个 bug 叠加造成了 89.4 cm 的巨误差；修完降到 **0.1 cm**——**四个数量级**。

## 5. 六个工程坑

| # | 坑 | 解决 |
|---|-----|------|
| 1 | 云端无屏 → 相机渲染不出来 | `xvfb-run -a -s "-screen 0 1280x1024x24"` |
| 2 | `Xvfb failed to start` | 上次残留锁文件 → `pkill Xvfb` + 删 `/tmp/.X*-lock` + 用 `-a` |
| 3 | gzserver `exit code 137` | 被 OOM 强杀（同时跑两个仿真），一次只跑一个 |
| 4 | 话题前缀是传感器名 | 用 `/wrist_depth_camera/*` 而非 `/camera/*` |
| 5 | 物体不持久 | 仿真重启后必须重新 spawn（写进世界文件可根治） |
| 6 | **自遮挡**：目标种在相机正下方会被腕部挡住 | 目标应偏光轴 15~20° |

## 6. 一条工程伦理底线（本项目明确立下的规矩）

方块被机械臂撞飞后，我曾提议把方块设成 `<static>（固定不动）`以便验证——**你当场否决了**：真实物理世界里物体就是会被撞动，不能为让测试通过而修改被测对象。

我接受并改为三条更严谨的做法：

1. **双视角一致性检验**——不依赖硬编码真值，从两个机位估计同一物体，结果应一致（物体在哪都成立）。
2. **证据驱动的搜索**——不猜物体在哪，以"是否真的看到"为唯一标准搜姿势（`pose_search_green.py`）。
3. **探针法**——用 TF 算出光轴落点，把目标精确种在视野里（`probe_spawn.py`）。

**这条规矩已写进项目长期记忆**：`不得为让验证通过而修改被测对象；物理真实优先`。面试时讲这一段，比讲任何一个技术点都更能体现工程素养。

## 7. 终局结论与已知环境限制

| 结论 | 依据 |
|------|------|
| **感知算法链路完全正确** | 全新世界、零位、单次测量误差 0.1 cm；传感器内部自洽性三组全对 |
| 残余异常是**环境问题** | 同一零位姿态，运动前后测出不同结果；估计点甚至不在"相机→方块"射线上 → 颜色图与深度图失配 |
| 对策 | **需要精确测量的场合，测量前 `killgaz + simcam` 重启仿真保纯净**（每次重启后首次测量已验证准确） |
| 真机影响 | 真机是 GPU 硬件渲染，不存在此类软渲染失配 |

### 高频追问

| 追问 | 回答要点 |
|------|---------|
| 为什么不用现成的视觉库（OpenCV/PCL）？ | 无 GUI 的云端环境下，我用纯 numpy 做颜色分割与点云解析，零依赖、可数值验证、便于讲清每一步；真机上会换成工程库。 |
| 手眼标定为什么自研？ | Tsai-Lenz 两步法本身清晰可讲；自研版用合成数据自测到机器精度（1e-16），比"能跑"更有说服力；且 eye_in_hand / eye_to_hand 双模式都验证过。 |
| 光学系约定怎么发现的？ | 比较"3D 点相对各轴的夹角"与"像素偏离图像中心的角度"——两者吻合的那个轴就是真正的光轴。 |
| 真机上这套能直接用吗？ | 数学链路通用；真机需补相机内参标定与实物手眼标定（AX=XB 已就绪），六维力传感器还可做力控抓取。 |
