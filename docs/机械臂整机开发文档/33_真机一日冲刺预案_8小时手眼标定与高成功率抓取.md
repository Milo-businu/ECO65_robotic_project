## 3. 手眼标定专项（最容易翻车，单独展开）

### 3.1 标定板与内参：一个已修、一个待验

**缺口 ①（今晚已修）：脚本原本只认棋盘格，你手里是 ArUco —— 明天会一组都检测不到。**
照片确认后，`collect_handeye.py` 已改为：

- **默认 `--board aruco`**：`cv2.aruco.detectMarkers` + `estimatePoseSingleMarkers`
- **`--aruco-dict auto`**：自动遍历 13 种常见字典，首次命中后锁定并打印 `dict=... id=...`
  → 现场不用猜你那张纸是哪个字典
- 每行打印**重投影误差**，`>2px` 会提示"这组建议重拍"（逐帧把关角点质量）
- `--marker-size` 用尺子实量的外框边长；`--marker-id` 可钉死某个标记
- 棋盘格模式保留（`--board chessboard`），两种板都加了重投影误差校验
- 云机实测 **OpenCV 4.2.0 自带 `cv2.aruco`**（`Dictionary_get` / `DICT_6X6_250` 都在），
  真机同环境，大概率直接可用。到场第一行若报 `cv2.aruco 不可用`：
  `pip3 install --user opencv-contrib-python==4.2.0.34`，或改用 `--board chessboard`
  （但你的板不是棋盘格，优先装 contrib）

⚠️ 现场别再改采集算法了。今晚已把`git pull`后就是最终版，一次只动一个变量。

**缺口 ②：内参目前直接用驱动发布的 `camera_info`（出厂值）。**
外部经验：出厂标定在 25℃ 做的，温度差异/使用久了会漂移；建议先单独验证内参再手眼，**禁止两个问题混合调试**。

现场快检（不单独做完整内参标定，够用即可）：
```bash
# 用同一块标定板，让相机从 0.35 / 0.5 / 0.7m 各看一次，卷尺量真实距离
# 对齐深度下取目标中心 10x10 像素的【中值】，别用单点
timeout 5 ros2 topic echo /camera/d435i/aligned_depth_to_color/image_raw > /tmp/d.txt
```
判据：0.5m 处深度误差 3–6mm 属正常；**若系统性偏 >1%（如整体短 4%）**，用 Intel Depth Quality Tool 做 tare 标定（先备份原标定）。若只是随机跳，用多帧中值 + 滤波（3.1 末）。

**深度滤波（低风险高收益）**：
```bash
# 先核对参数名（不同 realsense-ros 版本不同），不认就保持默认关闭
ros2 param list | grep -i filter
ros2 launch arm_grasp real_grasp.launch.py enable_depth_filters:=true start_task:=false
```
`spatial_filter` + `temporal_filter` 对静态桌面目标能明显压低飞点；`check_real_hw.py` 会直接报"有效深度比例"和"距离中值"，开完再跑一次对比。

### 3.2 采集策略：作业区聚焦版（按你确认的 1m×1m 作业区收窄）

你已确认：桌面/作业区约 **1m×1m**，方块放在机械臂周围不远、相机一定能看到的位置，
**时间不够不必做相机最高处的标定**。所以不用追求大范围/极限姿态 —— 这反而更准：
外部经验指出机器人 DH/绝对定位误差会让"在工作空间中心标定、跑到边缘用"偏掉，
**标定姿态覆盖的区域就应该等于抓取作业区**。

外部经验另有一条：**12 组高质量 > 20 组低质量**（只在一个平面平移时，20 组残差反而从 0.18px 升到 0.31px）。聚焦版采 **8–12 组**即可：

| 批次 | 主导运动 | 组数 | 要求 |
|---|---|---|---|
| ① | 台面中心附近 X 向平移 + 俯仰 | 3 | 标记覆盖图像中心与四角 |
| ② | Y 向平移 + 偏航 | 3 | 标记法线方向 **≥12°** 倾角变化 |
| ③ | 小幅度抬降 + 末端滚转 | 2–4 | **不必抬到最高处**；至少 2 个轴有激励 |
| ④ | 作业区四角各补 1 组 | 0–2 | 只在时间充裕时补 |

```bash
cd ~/robot_vla_ws
ros2 launch arm_grasp real_grasp.launch.py start_task:=false   # 终端 A（相机 + rm_driver + /joint_states）
timeout 3 ros2 topic echo /joint_states                        # 终端 B，先确认在刷

# 终端 B：采集（★ marker-size 用尺子实量的 ArUco 外框边长，单位米）
python3 recovery/collect_handeye.py --marker-size <实量边长> \
    --out ~/handeye_samples.json

# 采完【立刻】跑质量判据（--focused = 作业区聚焦模式）
python3 robot_code/arm_grasp/scripts/handeye_quality.py \
    --input ~/handeye_samples.json --focused
```

`--focused` 把样本数要求放到 8、轴覆盖阈值放到 12°，**但把打点验证升级为强制 ≥5 点**
（姿态激励弱了，物理打点就是唯一可信的兜底）。输出 `GO / 条件性 GO / NO-GO`。

采集时每行会打印 `dict=... id=... 重投影 X.XXpx`，**>2px 的组换个位姿重拍**，别将就。

### 3.3 求解与验证：残差小 ≠ 标定对

```bash
python3 recovery/handeye_calib.py --input ~/handeye_samples.json --pairs all
```

把输出的 4×4 填进 `real_params.yaml` 的 `handeye.matrix_4x4`，`calibrated: true`；求解器还会输出「推荐接法 flange→d435i_link」的 7 个数，填 `tf_xyz` / `tf_quat_xyzw`（**只给 RViz 用**，抓取计算不看它）。

**打点验证（聚焦模式下是硬门槛，不许跳过）**：让尖针/夹爪尖端去碰标定算出来的已知点。
按你 1m×1m 的作业区，就取这 **5 个点**（用台面孔阵定位，尺子量坐标）：

```
        (0.2, 0.8) ───────── (0.8, 0.8)      ← 远端两角
             │      (0.5,0.5)  │              ← 中心
        (0.2, 0.2) ───────── (0.8, 0.2)      ← 近端两角
```

```bash
python3 robot_code/arm_grasp/scripts/handeye_quality.py \
    --input ~/handeye_samples.json --focused --probe 2.1 1.8 2.6 3.0 2.4
```
判据：**5 个点全测、最大 <3mm**。残差再小，打点不过也不许进抓取。
只测中心一点是最常见的自欺 —— 作业区边缘的误差往往最大。

### 3.4 误差长什么样 → 查哪里（外部经验分层，很省时间）

| 现象 | 优先查 |
|---|---|
| 所有位姿**近似固定平移偏差** | 标定板实量尺寸、`tcp_offset`、静态变换、`w_max` |
| 误差方向**随机械臂姿态旋转** | 旋转估计、变换求逆顺序、时间同步、支架/线缆松动 |
| **只有画面边缘**变差 | 相机内参 / 畸变模型、镜头 |
| **运动时才**变差、静止准 | 图像与关节时间戳、曝光时刻、卷帘快门 |
| 数学残差正常但执行全错 | **坐标系定义**：`base→flange` vs `flange→base`、mm/m、欧拉角顺序、`xyzw` vs `wxyz` |

⚠️ 本项目已知的两个具体约定，现场别改：
- `collect_handeye.py` 输出 `quat_wxyz`；`real_params.yaml` 的 `tf_quat_xyzw` 是 **xyzw，w 在最后**
- 感知不依赖 TF 树，走 `p_base = FK(当前关节角) · X · p_cam`，**每次现算，禁止缓存**

## 5. 抓取率迭代方法（不是"多试几次"，是分层定位）

### 5.1 每次实验记一行（现场用纸笔或表格都行）

| # | 目标位置 | 感知 [x,y,z] | 打印的 TCP | 水平偏差 mm | 开口/堵转 | 结果 | 改了什么 |
|---|---|---|---|---|---|---|---|
| 1 | 中心 | | | | | ✅/❌ | 基线 |
| 2 | 中心 | | | | | | `interference 3→4` |
| … | | | | | | | |

**一次只改一个参数**，否则不知道是哪个起了作用。

### 5.2 故障树：先定位层，再调参数

```
抓取失败
├─ 感知目标本身偏 → 打点验证 ≥3mm？→ 手眼/内参/板尺寸；或颜色阈值/深度有效点
├─ 感知准但 TCP 偏  → 打印 TCP 与目标中心比较 → tcp_offset(0.177)、IK 分支、限位
├─ TCP 准但夹空      → interference_mm(3)、deadzone_deg 补偿、目标宽度、堵转是否触发
├─ 下降时撞/推走方块 → 下降终点 z、abort_on_target_shift_m、speed(≤20)、观察位姿
└─ 夹住后掉落        → 保持角度别发 stop、抬升速度、加大过盈、检查指面摩擦(贴防滑胶)

放置失败（第 9~11 阶段）
├─ 转运中途蹭到桌面/别的东西 → approach_height_m 抬高 → 但先跑 IK 可达性(preflight)
├─ 落点每次都偏同一方向     → place.xy 示教没对准中心 → 重跑 teach_place_point.py
├─ 方块落地翻倒             → release_gap_m 太大 → 0.008→0.004；或 surface_z 填高了
├─ 撤离时把方块带走         → 张开不够(open_width_mm 加到 100) / 指面粘 → 看日志开口变化
└─ 第 9 阶段直接报"无 IK 解" → 放置点太远或太高 → 往里挪 / 降 retreat_height_m
```

对应配置都在 `real_params.yaml` 一个文件里，改完**不用重新编译**。

### 5.3 调参优先级（从上往下，别跳）

1. `arm.speed` 降到 10（真机第一次）
2. `gripper.interference_mm` 3 → 4（顶得更紧，靠堵转）
3. `task.approach_height_m` / `descend_steps`（下降终点与步数）
4. `perception.min_pixels` / `depth_min_m` / `samples`（感知稳定性）
5. 最后才动 `tcp_offset`、`handeye.matrix_4x4`（这两个是标定结果，**不该用来"调"误差**）

### 5.4 统计量

- 第 1 轮：固定位置 **5 次**，≥3/5 才算链路稳
- 迭代后：≥4/5
- 泛化：3 个位置 × 两种目标物，≥80%
- 每轮把 `ros2 launch ... 2>&1 | tee ~/grasp_$(date +%H%M).log` 存下来，事后能对齐"哪次改了什么"

## 附录 C：VLA 大脑与「仿真方块 → 真机识别」的认知纠偏

> 2026-11-04 追加。外部资料为当日检索所得，这个领域半年一变，**以官方仓库为准**；
> 凡涉及本项目行为的结论，一律以 `robot_code/arm_grasp/` 里的实际代码为准。

### C.1 先纠正一个误解：本项目里「识别方块」不是 VLA 干的

```
你以为：  仿真方块/苹果模型 ──训练──> VLA ──识别──> 真机真实方块/苹果
实际：    仿真方块/苹果模型 ──只是 Gazebo 里的被测物──> 验证 IK/感知几何/夹持闭环
          真机识别 = perception_node.py 的 HSV 颜色阈值 + 对齐深度反投影（纯规则，零训练）
          VLA = 可选的高层策略，当前 task.policy: geometric、vla.enabled: false
```

- `perception_node.py` 用 `color_mask()` 按颜色分割（支持 `green/red/blue/auto`），
  再用 `camera_info` 内参把对齐深度反投影成 3D 点，取多帧中位数输出目标顶面中心。
  **它不是神经网络，没有用任何仿真数据训练过。**
- 仿真里生成的方块和红苹果是 **Gazebo 的被测物**，用来验证
  「IK 路径 → 笛卡尔下降 → 力矩夹持 → 吸附抬升」这条几何链，不是训练集。
- 所以「仿真训练 → 真机识别」这条链**在本项目里根本不存在**。
  真机能不能认出方块，取决于**现场光照下 HSV 阈值稳不稳 + 深度有没有洞 + 三条标定链**，
  与 Gazebo 里那个方块长得多像无关。

**这反而是好消息**：颜色+深度这种低维规则特征，对 sim2real 的视觉域差距
（纹理/渲染/光照）比学习式检测器更不敏感。外部资料里"只在随机化渲染上训练、
直接迁移到真机"的成功案例靠的正是域随机化；我们连这一步都不需要。

### C.2 ⚠️ 明天先别抓苹果（真实缺口，会浪费现场时间）

| 缺口 | 说明 |
|---|---|
| 没有苹果类别 | `color_mask()` 只认 `green/red/blue/auto`，配置里没有 apple/圆形物体类别 |
| 几何假设不对 | 感知按 `box_half_size_m`（4cm 正方体）算顶面中心；苹果是圆的、尺寸不同，下降终点会算偏 |
| 颜色冲突 | 真机苹果若是红/绿色，可能被当成红/绿方块误检（`target_color` 是单选） |

**明天只抓方块**（绿 / 红 / 浅蓝），苹果留到后续。第 5 节的抓取率统计与泛化实验
也只对方块做，别把苹果混进来，否则失败原因分不清。

后续要真识别真实苹果，三条路（都不在一天内做）：
① 零训练：给苹果单独的颜色阈值 + 圆形轮廓 + 独立尺寸参数（改 `perception_node.py`）
② 轻量检测器：加一台固定 USB 相机，YOLO/MobileNet-SSD 用几十张**真机照片**微调
③ 仿真域随机化训练检测器：工程量大，且必须有真机验证集兜底，性价比最低

### C.3 2026 年 VLA 主流与 RTX 3070 8GB 的显存账

主流开放权重/框架（2026-11 检索）：**LeRobot（HF）** 已是入门事实标准；
`openpi`（PI，JAX 为主）跑 π 系列；`Isaac GR00T` 是 NVIDIA 生态；
`openvla` 偏学术基线。模型侧 π0.5 / GR00T N1.7（3B 级）主打泛化，
**SmolVLA（450M）与 ACT（~80M）是消费级/边缘部署的主流答案**。

| 模型 | 参数 | 推理峰值显存 | 微调显存 | 延迟 | 3070 8GB 结论 |
|---|---|---|---|---|---|
| ACT | ~80M | <2 GB | 8 GB 轻松 | ~20 ms | ✅ 推理+微调都行 |
| Octo | 93M | <2 GB | 很小 | — | ✅ |
| **SmolVLA** | **450M** | **2–4 GB** | 单张消费卡（LoRA 更稳） | ~245 ms | ✅ **推理舒服**，微调建议 LoRA+小 batch |
| RDT-1B | 1.2B | 6–8 GB | 24 GB+ | — | ⚠️ 加上 CUDA context 就顶满 |
| π0 / π0.5（openpi） | 3.3B | 9–12 GB | LoRA >22.5 GB、全量 >70 GB | π0.5 ~485 ms | ❌ 放不下 / 微调别想 |
| OpenVLA 7B | 7B | 16–19 GB（4bit 7–9 GB） | 24 GB+ | 慢 | ❌ 4bit 也几乎满载 |
| GR00T N1.7 | 3B | A100/H100 80 GB 级 | 同左 | ~152 ms | ❌ 人形/全身，桌面臂过重 |

> 显存不只有权重：CUDA context + PyTorch runtime 先占 **1.2–2 GB**，
> 再加 KV cache 和视觉编码器激活。8 GB 卡实际可用约 **6–6.8 GB**。
> 所以"参数量看着能塞"不等于跑得动。

**关于"卡不卡"**：VLA 普遍 150–500 ms 一次推理，对 10–50 Hz 的控制环都偏慢。
实际做法是**预测一段动作块（action chunk，16–50 步）摊薄开销 + 异步推理**，
或者干脆用 ACT（20 ms）。真机上还要留显存给相机 pipeline 与 ROS，别把 8 GB 吃满。

### C.4 对本项目的明确建议

1. **明天绝对不要换 VLA**。`task.policy: geometric` + `vla.enabled: false` 是当前最稳的路；
   换成任何学习式策略都会引入一个远大于手眼标定的不确定项，与 8 小时目标直接冲突。
2. 后续若想玩 VLA，**3070 8GB 的正确选择是 SmolVLA（推理）或 ACT（微调+实时）走 LeRobot**；
   π0.5 留给云机/租 A100，或把 policy server 放云端、真机只发图收动作（远程推理）。
3. **比换模型更关键的是加一台固定 USB 摄像头**。`vla_policy.py` 的文件头已写明：
   π0 预训练吃「第三人称场景视角 + 腕部视角」双图，我们只有腕装相机，
   `vla_server.py` 把腕部图同时塞进 exterior 槽位，**只能验接口通不通，不保证效果**。
   腕装相机视角随臂动、抓取前看不到全局，这是VLA 效果的硬伤，不是模型选型能补的。
4. VLA 微调要的是**真机示教数据**（SmolVLA 最低 ~30 episodes、ACT ~50），
   不是仿真方块；仿真数据对 VLA 的价值受 sim2real 域差距限制。
5. 真机六维力话题（`/rm_driver/udp_six_force`）已确认后置，不作为 VLA 输入。

## 附录 D：明天到底怎么「认出真实方块」并抓取（照着做）

> 2026-11-04 追加。**不需要训练、不需要 VLA、不需要模型文件。**
> 要做的是把颜色阈值对准现场光照，然后让 5 道门全亮。

### D.1 识别其实是 5 步算术，不是"认"

`perception_node.py` 每 0.2 秒做一次：

| 步 | 做什么 | 用到的配置 |
|---|---|---|
| ① | 收彩色图 + 对齐深度 + 彩色内参 + `/joint_states` | `camera.prefix` / `*_suffix` |
| ② | **颜色分割**：绿=`g>100 且 g>r+40 且 g>b+40`（红/蓝同理） | `perception.target_color` / `color_thresholds` |
| ③ | 在命中的像素上取深度（**毫米 ÷1000 → 米**），过滤 `0.20<z<0.90` | `depth_min_m` / `depth_max_m` |
| ④ | 反投影 `p_cam=[(u-cx)z/fx, (v-cy)z/fy, z]`，再乘 `FK(当前关节角)·X` 转到基座系 | `handeye.matrix_4x4`（**每次现算 FK，禁止缓存**） |
| ⑤ | 取 99 分位 z 当顶面、只取顶面点算 xy 中心；最近 12 帧均值，水平抖动 >2cm 不发布 | `samples` / `jitter_max_m` |

发布 **`/grasp/target_xyz` = `[x, y, z]`（方块顶面中心，base_link 系）**，
同时发 `/grasp/target_xyz_pose` 给 RViz 看。

`grasp_task.py` 的 `ROSPerception.wait_target(25s)` 订阅它，要求 3 秒内有新数据；
拿到后减 `box_half_size_m` 得方块中心 → `planner.plan_grasp` 算 IK 直线下降 →
预夹 → 夹持 → 抬升。**没有任何一步在做图像分类或模型推理。**

⚠️ `box_half_size_m: 0.02` 是**已知几何**（4cm 方块），用来算预夹开口 40mm。
真机方块必须真是 4cm，否则夹持开口会算错。

### D.2 5 道门：`/grasp/target_xyz` 没数就按这个查

| 门 | 检查 | 不亮的原因 |
|---|---|---|
| 1 彩色图 | `timeout 5 ros2 topic hz /camera/d435i/color/image_raw` | 相机没起 / 前缀错 / USB2 带宽不足 |
| 2 对齐深度 | `timeout 3 ros2 topic echo /camera/d435i/aligned_depth_to_color/image_raw` | `align_depth.enable:=true` 没开 |
| 3 内参 | `camera_info` 有数据 | 相机没起 |
| 4 关节角 | `timeout 3 ros2 topic echo /joint_states` | **`udp_ip` 不是本机 IP**（最常见） |
| 5 手眼标定 | `handeye.calibrated: true` + `matrix_4x4` 已填 | **故意拒绝输出**，防止拿错坐标撞东西 |

另外三道"数据门"：颜色命中 < `min_pixels`(30)、mask 内有效深度点 <5、
多帧水平抖动 > `jitter_max_m`(2cm)。
**这三类以前是静默 `return`，现在每个都有节流诊断日志**，看感知节点的输出就知道卡在哪。

### D.3 到场 5 分钟对准流程

```bash
cd ~/robot_vla_ws && git pull gitee main
source /opt/ros/foxy/setup.bash && source ~/robot_vla_ws/install/local_setup.bash

# ① 起链路（不自动抓）
ros2 launch arm_grasp real_grasp.launch.py start_task:=false

# ② 先看 5 道门全不全（手眼没标完时第 5 道不亮是正常的）
python3 robot_code/arm_grasp/scripts/tune_perception.py --check-only --seconds 8

# ③ 把绿方块放到作业区、让它在彩色图里完整可见，然后可视化对准阈值
python3 robot_code/arm_grasp/scripts/tune_perception.py --color green
#    拖 min / lead1 / lead2 三个滑块，让方块被完整高亮、背景尽量干净
#    按 s 打印并保存建议阈值，按 q 退出
#    无桌面时用 --headless（只打印统计）

# ④ 把打印出来的 3 个数字填进 real_params.yaml 的 perception.color_thresholds.green
#    然后重跑感知节点（或重启整机 launch）

# ⑤ 确认出数
timeout 5 ros2 topic echo /grasp/target_xyz
```

**验收（这就是"认出来了"的判据）**：
打印的 `[x,y,z]` 与用尺子量的方块位置对得上（水平 <5mm），
且感知节点日志里的 `颜色命中 N px / 有效深度 M 点 / 距离中值 0.3~0.6m` 都合理。
`/grasp/target_xyz` 稳定有数了，才开 `start_task:=true`。

### D.4 认不出来时按现象查

| 现象 | 优先查 |
|---|---|
| `颜色分割只命中 0 像素` | 阈值不对（跑 `tune_perception.py`）/`target_color` 选错 / 现场光照与自动曝光漂移 |
| 命中很多像素但目标是背景 | 桌面有大片同色 → 别用 `auto`，钉死 `green` 并收紧阈值 |
| `mask 命中 N 像素但有效深度只有 M 个` | 目标 <0.28m 进盲区 / 反光 / `align_depth` 没开 / 深度 0 值 |
| `手眼标定未完成，拒绝发布` | 先做完 3.3 打点验证并填 `matrix_4x4`、`calibrated: true` |
| `收不到 /joint_states` | `rm_eco65_config.yaml` 的 `udp_ip` 改成 `hostname -I` 的本机 IP |
| 数字有但一直跳 | 多帧抖动 >2cm：关掉自动曝光/固定光源、目标别放在画面边缘 |
| 红/浅蓝方块认不出 | 改 `target_color` 并对准对应阈值（三种颜色各有一套） |

⚠️ **D435i 自动曝光/白平衡会让颜色漂移**：调好阈值后别再改光源、别拉窗帘到一半、
别让阳光直射方块。换光照就得重新对准一次，这比"训练一个模型"快得多，但要守规矩。
