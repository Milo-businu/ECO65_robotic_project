## 0. 一句话结论

**换机器只改一个文件：`robot_code/arm_grasp/config/real_params.yaml`。**
代码里没有任何 `/home/ubuntu`、没有任何写死的话题名、没有写死的串口。

搬家的正确顺序是：**先软件、后硬件** ——
在真机上接电之前，就跑 `preflight.py` 把「配置 → 运动学 → IK 规划 → 夹爪协议 → 完整状态机」全部验一遍。
硬件接上后剩下要做的只有**两项标定**（夹爪开口、手眼），标定完就能抓。

## 2. 和仿真比，真机到底差在哪（先搞懂，不然会白调一天）

| # | 项目 | 仿真（云服务器） | 真机 | 谁负责抹平 |
|---|---|---|---|---|
| 1 | 机械臂运动 | `FollowJointTrajectory` action | `/rm_driver/movej_cmd` **话题** | `arm_backend.py` |
| 2 | 关节角来源 | Gazebo 直接发 | rm_driver **UDP 主动上报**（`udp_ip` 填错就一点数据都没有） | 配置 `arm.udp_ip` |
| 3 | 相机姿态 | 写死的 `CAM_ROT`（相机相对 Link6） | **手眼标定 X**（4×4 矩阵） | `handeye.matrix_4x4` |
| 4 | 夹爪驱动 | effort 力矩（物理引擎才有） | 串口**位置模式**，夹持靠**堵转** | `gripper_node.py` |
| 5 | 夹持力 | 力指令 `0.030 N·m` | 目标开口比物体窄 3mm → 顶到停 | `interference_mm` |

### ⚠️ 最容易翻车的一条：别把 `eff_test.py` 直接搬到真机

睿尔曼给了 `rm_control` 包，能把 `FollowJointTrajectory` action 桥接成 CANFD 透传给真机——
看起来"仿真代码能直接用"。但它的 C++ 实现有两条硬要求：

1. 每个轨迹点必须有 `velocities` / `accelerations`（代码里直接索引 `[0]`）
2. 点数 > 3 才走三次样条插值分支

而仿真的 `eff_test.py` **只填了 `positions`**，真机上会越界崩溃。

> 本项目的处理：默认 `backend: movej`（不走 rm_control，最稳）；
> 若你确实用 action 后端，`ActionBackend` 会自动补齐速度/加速度并补点到 4 个以上。


## 6. 第 ③ 步：软件侧一键准备

```bash
cd ~/robot_vla_ws
bash restore_real.sh
```

这条脚本会做 5 件事，**每一步都幂等**（可以重复跑，不会搞坏）：

| 步骤 | 做什么 | 需要人做什么 |
|---|---|---|
| 1 | 检查 Ubuntu 20.04 / ROS2 Foxy | 没有就先按 26 号手册装 |
| 2 | 装 `python3-yaml numpy opencv pyserial` | 输 sudo 密码 |
| 3 | 写 udev 规则：夹爪固定成 `/dev/motor_serial` | **拨码开关 2 号打到 ON**（脚本做不了） |
| 4 | **先补编 `rm_ros_interfaces` / `rm_driver` / `rm_control`，再编 `arm_grasp`** | C++ 包约 1~3 分钟 |
| 5 | 跑 `preflight.py` 全链路自检 | 看输出，照着补 |

> ⚠️ **第 4 步为什么要补编依赖包（2026-11-03 真机实测踩到的坑）**
>
> 一开始脚本只跑 `colcon build --packages-select arm_grasp`，真机上直接报：
> ```
> ERROR:colcon.colcon_ros.task.ament_python.build:Failed to find the following files:
> - .../install/rm_ros_interfaces/share/rm_ros_interfaces/package.sh
> - .../install/rm_control/share/rm_control/package.sh
> - .../install/rm_driver/share/rm_driver/package.sh
> ```
> **意思**：`package.sh` 是包编译后生成的"环境钩子"，找不到 = 那三个包还没编过。
> colcon 在构建纯 Python 包时会检查它 `package.xml` 里声明的依赖包有没有这个钩子。
>
> **两处修复**（已做）：
> ① `package.xml` 把同工作空间的 C++ 驱动包从 `exec_depend` 里移除 ——
>    它们是**运行期**提供话题的节点，本包构建期根本不 import，列进来是错误耦合；
> ② `restore_real.sh` 显式检测并补编整机运行真正需要的三个包。
>
> 这三个包依赖很干净（只依赖 apt 的 `rclcpp` / `std_msgs` / `rosidl` + 彼此），补编不会连带编译整个工作空间。

### 如果 C++ 包暂时编不过：不编译也能跑

`arm_grasp` 是**纯 Python 包**，`preflight.py` / dry-run / 甚至整机 launch 都不需要它先编译。
脚本在第 4 步失败时会打印降级命令，也可以直接用：

```bash
# 离线自检与演练（完全不需要编译）
python3 ~/robot_vla_ws/robot_code/arm_grasp/scripts/preflight.py
python3 ~/robot_vla_ws/robot_code/arm_grasp/scripts/grasp_task.py

# 用【绝对路径】起整机（不写包名，就不需要 install/share）
source /opt/ros/foxy/setup.bash
ros2 launch ~/robot_vla_ws/robot_code/arm_grasp/launch/real_grasp.launch.py start_arm:=false
```

`start_arm:=false` 时即使 `rm_driver` 没编译，launch 也只会**告警并跳过**机械臂驱动，
相机 / 夹爪 / 感知节点照常起来，可以先验证话题链路。但**真要动机械臂，这三个包必须编好**。

### 夹爪接线三件事（脚本代劳不了）

1. 供电 **10~25V**，接"接口一" XH2.54 4Pin
2. USB-C 接电脑（**不支持热插拔**，先插好再上电）
3. ★ **拨码开关 2 号打到 ON**，1 号保持 OFF ——
   2 号不打 ON，串口**一个字节都收不到**，这是最容易怀疑"驱动写错了"的假故障

### preflight 输出怎么看

```
自检汇总：✅ N 项通过   ⚠️  M 项待办   ❌ 0 项失败
```

- `❌` 必须修完才能往下走
- `⚠️` 是流程步骤（未标定、未开真机开关），不是错误

## 7. 第 ④ 步：两项标定

### 7.1 夹爪开口标定（必须先做）

**为什么必须做**：夹爪只有位置模式，没有力控。夹持靠「让目标开口略小于物体宽度，
手指顶到物体后电机堵转自动停」。角度→开口换算不准，就会夹空或一路顶死。

> ⚠️ **跑这一步时不要开着整机 launch**。`calibrate_gripper.py` 直接独占串口，
> 而 `real_grasp.launch.py` 会起 `gripper_node.py` 占着同一个 `/dev/motor_serial`，
> 两边抢串口会打不开。夹爪标定**不需要起 ROS**，直接跑脚本即可。
> 另外这三步都会**真的动夹爪**，手指别放在两指之间。

```bash
cd ~/robot_vla_ws/robot_code/arm_grasp/scripts

# ① 先看一遍怎么玩（不接硬件，演示拟合算法）
python3 calibrate_gripper.py --demo

# ② ★ 先验证「发 300° 是否真的走 300°」（不用尺子，强烈建议先跑）
python3 calibrate_gripper.py --verify --port /dev/motor_serial

# ③ 正式标定（需要一把尺子，约 10 分钟）
python3 calibrate_gripper.py --port /dev/motor_serial
```

流程：让夹爪张开到底 → 量最大开口 → 每次闭合 300° 量一次，记 5 组 →
脚本最小二乘拟合出 `deg_per_mm`。

#### 「每次 300° 我怎么控制精准？」—— 不用你控制，也别信指令值

- **指令本身是精确的**：角度字段单位是 0.1°，300° 就是 `3000` → 两字节 `0x0B 0xB8`，
  整帧 `7b 01 02 01 20 0b b8 00 c8 22 7d`。步进电机按脉冲数走路，
  32 细分下分辨率约 **0.056°/微步**，比指令分辨率还细，所以「发得准不准」不是问题。
  按一下回车，脚本就把这条帧发出去了，**你不需要手动微调**。
- **真正会出错的是丢步 / 堵转提前停**（顶到东西、`--speed` 太快、供电不足）。
  这时「我以为走了 300°」和「实际走了 300°」就不一样，
  拿指令值去拟合，`deg_per_mm` 会系统性偏掉。
- **所以脚本现在每次闭合后都会回读电机累计角度**（发 `CMD_QUERY`），
  以 home 后的读数为基准做差分，用【实际角度】拟合；
  同时打印「指令累计 / 实际累计 / 差值」，偏差超过 5° 直接判定本次标定**不可信**并退出。
- **第 ② 步 `--verify` 就是专门查这件事的**：连发几次 300°，只回读、不量开口。
  增量稳定 ≈300° 才继续；若稳定是 30° 或 3000°，是反馈倍率解析差 10 倍
  （手册表 3-15 有这个疑点），加 `--feedback-scale 10` 或 `0.1`；
  若忽大忽小，是丢步 → 把 `--speed` 从 20 调到 10、确认供电 10~25V、手指别卡住。

> 一句话：**标定的角度这一侧必须是「读回来的真值」，不能是「发出去的意愿」。**

#### ★ 模型不是简单线性：有「机械空程」（2026-11-03 真机实测修正）

真机丝杠/齿轮有间隙：**电机先空转约 105° 手指才动**，之后才严格线性，
接近最小开口又会撞机械限位。所以一组健康的实测数据长这样：

```
130, 114, 97, 77, 57, 37, 17, 10 mm     （每 300° 采一次）
每段变化：16 / 17 / 20 / 20 / 20 / 20 / 7 mm
          └ 起始过渡 ┘ └─ 线性区，每 300° 恰好 20mm ─┘ └ 限位
```

**前两段偏小、最后一段偏小是正常的，不是读数错，也不是模型错。**
旧版脚本用 `angle = (w_max − w) × k` 强制过原点，把这 105° 硬塞进斜率里 →
deg_per_mm 被系统性拉偏、残差 10mm 以上。现在改成带空程的分段线性：

```
angle(w) = deadzone_deg + (max_width_mm − w) × deg_per_mm
w(angle) = max_width_mm − max(0, angle − deadzone_deg) / deg_per_mm
```

拟合用**中位数**求斜率与空程角，天然剔除起始过渡段和末端限位段；
残差判定只看稳定段。用上面这组数据实算：`deg_per_mm=15.0000`、
`deadzone_deg=105.0`、**稳定段残差 0.00mm**。

把输出的**四行**填进 `config/real_params.yaml` 的 `gripper` 段：

```yaml
  calibration_done: true
  max_width_mm: 130.0
  deg_per_mm: 15.0000
  deadzone_deg: 105.0
```

⚠️ **填之前先看「稳定段最大残差」**：脚本会打印逐点残差表并标出
`← 重点复查` 的组；起始过渡与末端限位会标注「不参与判定」。
残差 > 3mm 会判定不可信并**拒绝输出配置值**，这时别填、按提示重标。
注意 `w_max` 超过夹爪标称 **10~120mm**（例如量到 130）时先确认量的是
两指尖**内侧**、尺子贴平，别量到外侧。

⚠️ **从 home 出发的第一次闭合**要多走 `deadzone_deg` 度；之后连续闭合的
增量里空程会相互抵消。`gripper_node.py` 已按这个规则处理，别自己改。

#### 验收（空夹验证）：`grip:40` 不是终端命令

**`grip:40` 直接敲进终端会 `command not found`。** 它是发给夹爪节点的
**话题消息内容**，含义是「按物体宽度 40mm 夹持 → 目标开口 =
40 − `interference_mm`（默认 3mm）= **37mm**」。三种等价做法：

```bash
# ① 最省事：标定脚本拟合成功后会直接问「现在做空夹验证吗？」，回车即可
#    它用刚拟合出的 deg_per_mm 直接走串口，不用起 ROS、不用先填配置

# ② ROS 话题方式（需先起 gripper_node.py）
ros2 topic pub --once /gripper/cmd std_msgs/msg/String "data: 'grip:40'"
#    ⚠️ pub 支持 --once；echo 不支持，别搞混

# ③ 网页方式（真机新增）
python3 robot_code/arm_grasp/scripts/gripper_node.py &
python3 robot_code/arm_grasp/scripts/gripper_web.py
# 浏览器打开 http://127.0.0.1:8777，输入 40 点 Grip
```

量实际开口，与 37mm 差 **<2mm** 算通过；差得多就别填配置，重标或微调 `deg_per_mm`。

### 7.2 手眼标定（不做就抓不了）

按 `25_手眼标定操作清单.md` 做，要点三个：

- 棋盘格**固定在桌面**，标定期全程不许动
- 位姿**必须有旋转差异**（每组转 20°~60°），只平移解不出旋转
- 方格边长**用尺子实量**（打印有误差）

#### ⚠️ 先搞清楚：法兰位姿不能靠 TF

真机的 `rm_driver` **不发布 TF 树**（只有 Gazebo 的 launch 里有静态变换），
所以采集脚本早期那版用 `tf2` 查 `base_link → flange` 在真机上必然报
`TF 读取失败`；而且它查的 frame 名（`base_link`/`flange`）和 URDF 里的
（`baselink`/`Link6`）也不一致，就算有 TF 也会带一个固定偏差。

**现在 `collect_handeye.py` 默认走 `fk` 模式**：用 `/joint_states` 的当前关节角
+ 随包 URDF 做正运动学算 `T_base←Link6`，和 `perception_node.py` 用的是
**完全相同的一套坐标**，不依赖 TF、也不会有 frame 名对不上的问题。

#### 前置（开两个终端，缺一不可）

```bash
# 终端 A：起相机 + 机械臂驱动（给彩色图、camera_info、/joint_states）
source /opt/ros/foxy/setup.bash && source ~/robot_vla_ws/install/local_setup.bash
ros2 launch arm_grasp real_grasp.launch.py start_task:=false

# 终端 B：确认关节角在刷（没数据 = udp_ip 没填本机 IP，见第 8 节第 2 项）
timeout 3 ros2 topic echo /joint_states
```

> 手眼标定现在**由脚本自动扫位**（`collect_handeye.py --sweep`：机械臂自己走 15 个位姿）。
> ⚠️ 因为 Ubuntu 不适配示教器、扫位由程序下发 movej，所以**标定前就要把
> `allow_arm_motion` 改 true**；`start_task` 仍保持 false（别在这步跑抓取）。

#### 采集与求解

```bash
cd ~/robot_vla_ws

# ★ 0) 先把 arm_ip / udp_ip 配对好（/joint_states 没数 90% 是这里）
python3 robot_code/arm_grasp/scripts/net_autoconf.py

# 采集：--camera-prefix 留空，脚本会从 real_params.yaml 读（和 launch 反推的
#        namespace 永远一致，不用自己猜）；按回车采一组，q 结束
# ★ 现场是 A4 ArUco 板：默认 --board aruco，边长必须用尺子量外框
python3 recovery/collect_handeye.py --marker-size 0.0595 \
    --out ~/handeye_samples.json

# 采完立刻判质量（--focused = 作业区聚焦模式）
python3 robot_code/arm_grasp/scripts/handeye_quality.py \
    --input ~/handeye_samples.json --focused

# 求解 + 自动写回配置（保留注释、自动备份、含"一眼假"自检）
python3 recovery/handeye_calib.py --input ~/handeye_samples.json \

```

启动时应该看到这一行，确认走的是 FK 而不是 TF：

```
 法兰位姿: FK(/joint_states → URDF baselink→Link6)  话题 /joint_states
```

#### 把结果填进配置

**推荐用 `--write-config` 自动写**（它改 `calibrated` / `matrix_4x4` / `tf_xyz` /
`tf_quat_xyzw` 四处，保留全部注释，并在旁边生成 `.bak` 备份）。

想手动改也行，形状是这样（`matrix_4x4` 是行优先的 4 行，每行 4 个数）：

```yaml
handeye:
  calibrated: true
  matrix_4x4:
    - [0.91961199, -0.12511545, -0.37237068, 0.05000000]
    - [0.00006866, 0.94797425, -0.31834700, 0.00000000]
    - [0.39282794, 0.29273015, 0.87177708, 0.13000000]
    - [0.00000000, 0.00000000, 0.00000000, 1.00000000]
```

> 上面的数字**只是形状示例**（真机不会是这几个数），用你自己求解的结果。

求解器还会输出一条「推荐接法：`flange → d435i_link`」的
`static_transform_publisher` 命令，把那 7 个数
（x y z qx qy qz qw，注意 **w 在最后**）填进
`handeye.tf_xyz` / `handeye.tf_quat_xyzw`。
⚠️ 这条静态 TF **只给 RViz / tf2_echo 可视化用**，抓取计算不看它
（感知直接用 `FK · matrix_4x4`），所以不填也能抓，只是 RViz 里看不到相机。

> ⚠️ **这不是可选项**。标完必须做"打点验证"。**不要用尺子硬量**
> （没有基准边，量不到 1mm 级），用脚本：
>
> ```bash
> python3 robot_code/arm_grasp/scripts/verify_handeye.py --points 5 --marker-size 0.0595
> ```
>
> 它把指尖开到"相机算出来的标记中心"上方 2cm，你用脚本自带的键盘微调把指尖挪到正好压住标记中心，
> 回车。脚本读那一刻的**关节角**反算指尖真实位置（完全不经过相机），得到误差 c。
> 4 个点都测：
> - c 一致（去均值残差 <5mm）→ 输出一行 `perception.xy_bias_m`，填进去就能抓
> - c 忽大忽小 → 是旋转/尺度问题，补不了，必须重标
>
> 为什么不是拿方块当基准：方块是被测对象，拿它的真值校程序就是作弊。
> ArUco 是标定基准物，用它做参考是标定的正常做法。

打开 `robot_code/arm_grasp/config/real_params.yaml`，改下面这些：

| # | 键 | 改成什么 | 不改会怎样 |
|---|---|---|---|
| 1 | `arm.arm_ip` | 机械臂实际 IP（默认 `192.168.1.18`） | 连不上机械臂 |
| 2 | `arm.udp_ip` | **真机 PC 的实际 IP**（`hostname -I` 查） | `/joint_states` **永远没数据**，感知全废 |
| 3 | `camera.prefix` | 跑 `ros2 topic list \| grep d435i` 看实际前缀 | 感知收不到图 |
| 4 | `camera.serial_no` | 相机序列号（建议填） | 多设备时可能开错相机 |
| 5 | `gripper.port` | `/dev/motor_serial` 或实际 `/dev/ttyUSB0` | 夹爪节点起不来 |
| 6 | `gripper.deg_per_mm` + `deadzone_deg` + `max_width_mm` + `calibration_done` | 标定输出的**四行**（含机械空程角） | 夹持开口算不准 |
| 7 | `handeye.matrix_4x4` + `calibrated` | 标定结果 | 感知拒绝出坐标 |
| 8 | `task.observe_joints` | 用 `jog.py` 把臂摆到"相机能俯视桌面"的姿势，按 `c` 打印观察位 | 观察姿势看不到桌面 → 感知找不到目标 |
| 9 | **`robot.tcp_offset`** | **法兰面 → 两指尖连线中点的实测距离**，沿工具 z 轴。2026-11-03 真机实测 **17.7cm**（`[0,0,0.177]`），不是早期估计的 19.5cm | 错 1.8cm → IK 下降终点偏 1.8cm，可能撞方块或夹空 |
| 10 | `gripper.min_width_mm` | 实际最小开口（标称 10mm，以实机为准） | 末端限位点误判、夹持目标开口算成负值 |
| 11 | `place.xy` | 放置区中心的地面 x/y，用 `teach_place_point.py` 示教读出 | 放歪/放到台外，IK 可能直接无解 |
| 12 | `place.surface_z` | 放置台面高度（方块底面落点）。桌面与基座同高填 `0.0` | 填高 1cm = 方块多掉 1cm（会歪）；填低 = 压台面 |
| 13 | `safety.cable_envelope_m` | **线缆包络**（约束法兰）：x/y/z 三个区间。本机实测 x 0~0.50、y ±0.20、z 0~0.50 | 不填就没人拦你，超出去会拽线；填错会白白拒绝合法动作 |

> ⚠️ **`tcp_offset` 与仿真 URDF 里的 0.195 不矛盾**：0.195 是 Gazebo 模型
> 「本体 0.145 + 指长 0.05」的建模值，只用于仿真；真机 FK 算到 `Link6` 后
> 直接加 `real_params.yaml` 里的 `tcp_offset`。两者独立，改真机配置即可。

> **第 8 项怎么读**：把臂摆好后，在终端跑
> `timeout 3 ros2 topic echo /joint_states`（Foxy 的 `echo` **没有** `--once`），
> 从 `position: [...]` 里抄出 joint1~joint6 的 6 个弧度值，按 `joint1, joint2, ...` 顺序填。
> 观察位姿**不做 IK**——真机上是摆出来的姿势，硬解"工具竖直向下"会无解（自检实测踩到）。

### 8.1 「观察位」到底是什么，能不能省掉

**它是什么**：一个**固定的 6 个关节角**，作用只有一个——让腕装相机能
**完整俯视作业区**，且这时夹爪/小臂不挡视野。整条流程里它出现在"回 home"之后、
"感知"之前，就是**抬起手看一眼**的动作。它不参与抓取计算，只决定"这一帧画面拍得好不好"。

三个硬条件（不只是"能看见"）：

| 条件 | 为什么 | 不合格的表现 |
|---|---|---|
| 目标在彩色图里 | 颜色分割是唯一的识别手段 | `/grasp/target_xyz` 没数，日志说"命中像素 0" |
| 目标距离在 **0.28~0.90m** | D435i 有效深度范围，0.3~0.6 最稳 | 有彩图没深度 → 反投影出 NaN/0 |
| 目标靠近画面中心、无遮挡 | 边缘畸变大、夹爪挡一半视野 | 坐标抖、偏一边 |

**能不省？分两种情况：**

- **能省**：如果你实测发现 **home 位姿本身就满足上面三条**（相机高
  0.72m 时桌面大约在 0.5~0.7m，正好在深度范围内），那就把
  `task.observe_joints` **填成和 `robot.home_joints` 一样的值**。
  状态机会照常执行这一步，但因为目标=当前，实际不动，等于跳过。

  ```yaml
  robot:
    home_joints: [0.0, 0.2, 0.3, 0.0, 0.0, 0.0]
  task:
    observe_joints: [0.0, 0.2, 0.3, 0.0, 0.0, 0.0]   # ← 和 home 一样 = 实际不移动
  ```

- **不建议省**：如果 home 是个"收缩姿态"（臂竖着、相机朝墙），那一步就不是
  多余的——它同时干了两件事：① 把相机带到能看桌面的角度；② 把臂带到离目标
  **更近的预备姿态**，让后面切到"工具竖直向下"的第一跳不至于太大。
  这一跳（日志里的 `initial_jump`）在真机上就是"整条手臂扫过去"，
  3cm 之外有东西就有撞的风险。

**怎么判断你自己的机器属于哪种**（现场 2 分钟）：

```bash
# 1) 把臂摆到 home，看相机画面里作业区是不是完整的（有画面就行）
ros2 run rqt_image_view rqt_image_view /camera/d435i/color/image_raw
# 2) 看深度是不是有效（有效比例低会显示"深度无效"）
python3 robot_code/arm_grasp/scripts/check_real_hw.py
# 3) 看第一跳多大：dry-run 里 diagnostics 的 initial_jump，> 1.0 rad 就别省
python3 robot_code/arm_grasp/scripts/grasp_task.py --dry-run | grep -i "跳变"
```

> 一句话：**能省的条件是"home 就看得见 + 第一跳不大"，不是"理论上任意姿态都能算"**。
> 因为手眼矩阵 X 虽然是常量，但"看得见"和"动作幅度小"是两件工程问题，不是数学问题。

最后开两道锁（`mode: real` 真机已经改好了，只要把第二道打开）：

```yaml
profile:
  mode: real                 # 已由真机改好，确认一下即可
  allow_arm_motion: true     # ← 只有这一行还需要你改
```

> 小工具：`python3 scripts/preflight.py` 会逐项提醒哪些还没填。
> ⚠️ 2026-11-04 起（无示教器）：**标定阶段就要打开 `allow_arm_motion: true`**，
> 因为扫位采集由程序下发 movej（夹爪开口标定仍只用串口、不动臂）。
> 两道锁同时打开时务必：工作区清空、急停在手边、`arm.speed ≤ 10`。

### ⚠️ 仓库里的 `real_params.yaml` 目前是「真机版」

真机已经把 `profile.mode` 改成 `real`（并填了本机 IP / 标定值）提交进仓库。
所以：

## 10.1 放置：抓完之后放到固定区域

抓取只解决"拿到手"，**放置才是任务的终点**。2026-11-04 补上这一段。

### 和抓取最大的不同：放置点不靠视觉

| | 抓取 | 放置 |
|---|---|---|
| 目标从哪来 | 感知每帧算（会变） | **配置里写死**（不变） |
| 属于什么 | 感知结果 | **标定结果**，量一次长期用 |
| 精度要求 | 厘米级（4cm 方块） | 同样厘米级，但**错了不会自我纠正** |

所以放置点必须**示教出来**，不能手估——手估错 1cm，每次都歪 1cm，而且没有任何反馈能救。

### 示教放置点（2 分钟）

```bash
cd ~/robot_vla_ws
python3 robot_code/arm_grasp/scripts/teach_place_point.py
```

1. 等它打印 `✅ 收到关节角 [...]`
2. 用 `jog.py` 把**指尖**移到放置区中心，**刚好碰到台面**（不是悬空、不是压进去）
3. 回终端按**回车**
4. 把打印出来的两行抄进 `real_params.yaml` 的 `place` 段：

```yaml
place:
  xy: [0.3215, -0.1987]     # ← 抄脚本输出
  surface_z: 0.0213         # ← 抄脚本输出
```

> ⚠️ 指尖 ≠ 法兰。脚本已经自动加上 `robot.tcp_offset`（17.7cm）并做了旋转，
> **不要自己拿卷尺量法兰位置填进去**。
>
> 💡 放置区有几个角、想确认台面平不平：加 `--multi` 连续采几个点，
> 脚本会告诉你 x/y/z 的范围；z 相差 >5mm 说明台面不平或某次没真碰到台面。

### 状态机多了哪三个阶段

```
… [8] 直线抬升（夹着方块）
    [9] 转运：原地竖直抬到 0.16m（台面以上）→ 水平平移 21cm → 竖直降到释放点
    [10] 张开夹爪释放（同时对比开口变化，判断方块有没有真的脱手）
    [11] 竖直撤离到 0.18m →（可选）回 home
```

**为什么第 9 步要拆成"抬—移—降"三段**：夹着方块直接走关节空间，方块会沿弧线
飞过去，中途可能扫地、撞台面、撞别的方块。所以照搬抓取那套思路，
全程用密集笛卡尔路径点，姿态固定"工具 z 竖直向下"。

### 三个高度别搞混（这是最容易错的地方）

```
        ┌─ retreat_z = surface_z + retreat_height_m  (0.20)   ← 撤离高度
        │
        ├─ travel_z  = surface_z + approach_height_m (0.18)   ← 转运高度
        │
        ├─ center_z  = surface_z + 半边长            (0.04)   ← 方块中心
        └─ release_z = center_z  + release_gap_m     (0.048)  ← 实际停在这
                                            ↑
              TCP 到这里时方块底面离台面 8mm，张嘴后轻落，不磕台面
```

- `surface_z` 填高 1cm → 方块多掉 1cm，会歪
- `surface_z` 填低 1cm → 指尖压进台面，可能顶到桌子/触发堵转
- `approach_height_m` 太低 → 转运时方块扫地（`preflight` 会自动把它顶高并提示）

### 三道自检（跑 preflight 会自动做）

```bash
python3 robot_code/arm_grasp/scripts/preflight.py
```

1. **可达性**：从抬升终点走到放置点，逐点 IK；有解才 ✅
   （实测 `xy=[0.32,-0.20]` + `surface 0.02` 时，**z 上限约 0.20**，
   再高 IK 就无解——所以 `retreat_height_m` 别乱设大）
2. **连续性**：相邻点关节跳变 < 1.0 rad，否则会突然翻腕
3. **限位余量** > 0，贴限位直接拒绝执行

### 第一次试放怎么做（分两步，别一上来就夹方块）

**第 ① 步：空爪跑一遍。** 桌面只放一个方块，`arm.speed: 20`，
`start_task:=true` 直接跑。空爪也会走完 11 个阶段（只是夹不到东西），
你要看的是：机械臂走的是不是"抬—移—降"那条你预期的路，落点是不是放置区中心。

**第 ② 步：夹着方块跑。** ① 确认无误后，把方块放回抓取位置再跑一遍。
这一次才真正检验"抓得住 + 放得下"。

> 为什么不直接夹着跑：空爪跑时即使路径算错也只是撞空，
> 夹着方块跑时算错 = 方块被扫飞/砸到台面。多花 40 秒，省一次摔东西。

### 如果放完方块歪了/被带走

| 现象 | 原因 | 改哪 |
|---|---|---|
| 方块落地翻倒 | `release_gap_m` 太大 | 0.008 → 0.004（但别小于 0.002） |
| 撤离时方块被带起来 | 指面有粘性/张开不够 | 查日志"开口 → mm"，把 `open_width_mm` 加到 100 |
| 每次都偏同一方向 1~2cm | `place.xy` 示教时没对准中心 | 重跑 `teach_place_point.py` |
| 放置点 IK 无解 | 点太远/太高 | 把放置区往里挪，或降 `retreat_height_m` |
| 转运中途撞到东西 | 转运高度不够 | `approach_height_m` 加到 0.18~0.20（但要先过可达性） |

## 11. 坑速查表（按"看起来像什么"排列）

| 现象 | 真因 | 处理 |
|---|---|---|
| `ros2 topic hz /d435i/...` 说没发布 | 话题其实叫 `/camera/d435i/...`（前缀坑） | `ros2 topic list \| grep d435i` 看真名 |
| Foxy 报 `unrecognized arguments: --once` | `ros2 topic echo` 没有 `--once`（Galactic 才加） | 用 `timeout 5 ros2 topic echo` |
| `/joint_states` 一条都没有 | `udp_ip` 填的是示例 IP 不是本机 IP | `hostname -I` 查，改配置里 `arm.udp_ip` |
| 夹爪毫无反应 | 拨码 2 号没打 ON / 没供电 / 端口名不对 | 检查三件事；`ls /dev/ttyUSB*` |
| 夹爪报权限拒绝 | 用户在 `dialout` 组但没重登 | `sudo usermod -aG dialout $USER` 后**注销重登** |
| 感知提示"手眼未标定" | `handeye.calibrated` 还是 false | 这是安全设计，先标定 |
| 抓取点整体偏一个固定量 | 标定时的 flange frame ≠ FK 的 tip_frame | 本项目统一用 `Link6`，别改 `tip_frame` |
| IK 报"高点无解" | `approach_height_m` 太大（真机夹爪 17.7cm） | 调到 0.14~0.16 |
| 抓取点整体低/高约 1.8cm、下降撞方块 | `tcp_offset` 用了旧值 0.195（仿真建模值），真机实测是 **0.177** | 改 `robot.tcp_offset: [0.0, 0.0, 0.177]`，用尺子从法兰面量到两指尖连线中点 |
| 标定数据「前两段只变 16/17mm、最后一段只变 7mm」、残差 10mm+ | 不是读数错，是**机械空程 + 末端限位**；旧版强制过原点的模型把空程塞进了斜率 | 用新版带 `deadzone_deg` 的模型（中位数拟合），稳定段残差应 ≈0；填四行配置 |
| 从 home 出发第一次闭合没到位、少走约 7mm | 没补 `deadzone_deg`（电机先空转、手指不动） | `gripper_node.py` 已自动在从 max_width 起步时补空程角 |
| 真机用 action 后端崩了 | rm_control 要速度/加速度且 >3 点 | 换回默认 `backend: movej` |
| 相机只有几 Hz | 插在 USB2 口（480M） | 换 USB3 口/线，`lsusb -t` 看 5000M |
| 深度图大面积空洞 | 太近（<0.28m）或物体吸光 | 拉远、换浅色物体、补光 |
| 单位差 1000 倍 | 深度图是毫米 | 代码已 `/1000`，别再除一次 |
| `colcon build` 报 `Failed to find .../package.sh`（rm_ros_interfaces / rm_control / rm_driver） | 这三个 C++ 包还没编译过，`package.sh` 是编译后才有的环境钩子 | `cd ~/robot_vla_ws && colcon build --packages-select rm_ros_interfaces rm_driver rm_control --symlink-install`；`restore_real.sh` 已自动做 |
| `ros2 launch arm_grasp ...` 找不到包 | 包没 `colcon build`，`install/share` 里没有 launch 文件 | 用绝对路径：`ros2 launch ~/robot_vla_ws/robot_code/arm_grasp/launch/real_grasp.launch.py` |
| 云服务器跑 `grasp_task.py` 卡住 / 去连不存在的机械臂 | 真机把 `real_params.yaml` 的 `mode` 改成 `real` 并提交了，云机也跟着按真机模式走 | 演练一律加 `--dry-run`：`python3 .../grasp_task.py --dry-run` |
| 手眼采集报 `TF 读取失败 (base_link -> flange)` | 真机 `rm_driver` 不发布 TF，且 frame 名与 URDF 不一致 | `collect_handeye.py` 默认已改走 `--flange-source fk`（用 `/joint_states` + URDF FK），确认启动时打印的是 FK 那行 |
| 夹爪标定报串口打不开 / `Permission denied` | 整机 launch 里的 `gripper_node` 占着同一个串口 | 标定前**不要起整机 launch**；标定脚本直接独占串口，不需要 ROS |
| 手眼采集提示「收不到 /joint_states」 | `rm_eco65_config.yaml` 的 `udp_ip` 不是本机 IP，或驱动没起 | `hostname -I` 查本机 IP 填进去；先 `timeout 3 ros2 topic echo /joint_states` 确认 |
| 终端敲 `grip:40` 报 `command not found` | `grip:40` 是发给夹爪节点的**话题消息内容**，不是 shell 命令 | 标定脚本成功后直接回车做空夹验证；或 `ros2 topic pub --once /gripper/cmd std_msgs/msg/String "data: 'grip:40'"` |
| 标定结果「最大残差 11.9mm」 | 某几组尺子读错 / 手指打滑 / 没等停稳 | 看逐点残差表里 `← 重点复查` 的组，按提示重标（`--wait 3.5 --points 7`），**别把结果填进配置** |

## 12. VLA（OpenPI π0）现在能做什么、不能做什么

**能**：接口是通的。`vla_policy.py` 调 `http://127.0.0.1:8000/predict`，
配置里 `task.policy: vla` + `vla.enabled: true` 就能让状态机走 VLA 分支。

**不能**：效果不保证。π0 预训练时吃的是「第三人称场景视角 + 腕部视角」双图，
本项目只有腕装相机，`vla_server.py` 会把腕部图同时塞进场景槽位——
等于让一个人把眼睛贴在手背上找东西。

**建议**：先用 `task.policy: geometric`（默认，稳）把抓取跑通；
VLA 若要用，**加一台几十块的固定 USB 摄像头**当场景视角（17 号文档第 7 节）。

## 14. 一句话总结

**移植的本质不是"把文件拷过去"，而是"把机器相关的东西全部收拢到一个配置文件里"。**
本项目做到了这一点：`real_params.yaml` 是唯一真相源，
`arm_backend.py` 是仿真与真机的唯一接口断层线，
`preflight.py` 让你在接电之前就知道代码层面通不通。

剩下要人做的只有两件：**用尺子量（夹爪标定）** 和 **拿标定板晃（手眼标定）**。
